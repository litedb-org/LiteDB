# Regression fixtures written by released LiteDB packages

The fixtures below were written for PR #3027 (IO regressions since 5.0.21) by the published
LiteDB 5.0.21 NuGet package, not by this repository's engine. The tests that read them assert
how the current engine reads, migrates or refuses real files of that version. This file records,
per issue #3034 §5, the producer, the generator, the runtime, the configuration, any bytes
changed afterwards, the pinned hashes, the expected outcome and why each fixture is kept.

## Location

The archives are not committed to this repository. They live in
[`litedb-org/LiteDB-Artifacts`](https://github.com/litedb-org/LiteDB-Artifacts) under
`compatibility/fixtures/<archive>`, at the revision `Resources/artifacts.json` pins together with
each archive's SHA-256. Tests resolve them with `ArtifactFixtures.Path("<archive>")`
(`$LITEDB_ARTIFACTS_DIR/<path>` when set, else a per-user cache, else a download of the pinned
revision); `scripts/test-5021-regression-compatibility.py` resolves them the same way. Every
resolved file is verified against its pinned hash.

This file lists the fixtures that are pinned there; each PR that adds a fixture adds its section.

The generator was rebuilt from the recorded commands of the session that made the fixtures
(the original scratch programs were not kept): `tools/RegressionFixtures5021` writes each
`*_5_0_21.zip`'s entries, one subcommand per fixture.

## Environment

All files were written on 2026-09-27/28 (UTC) on Linux x64: Ubuntu 24.04.4 LTS, kernel 6.18.44,
ext4. The .NET SDK was 10.0.401 with runtimes 10.0.12 and 8.0.31. `LANG` was unset, so the
current culture was the invariant culture and 5.0.21 stored collation LCID 127 with IgnoreCase
in every header. The generator pins the invariant culture, so any host writes the same
collation.

The original programs targeted two frameworks, which decided the runtime:

| Runtime | Fixtures |
| --- | --- |
| .NET 10.0.12 (`net10.0`, Release) | WalCrash, EncryptedWalCrash |
| .NET 8.0.31 (`net8.0`) | ConcurrentWalCrash, ForeignWal |

Both runtimes load the same package assembly. The generator targets `net8.0`. To run it on
.NET 10 as the first group was, set `DOTNET_ROLL_FORWARD=LatestMajor`. Child processes inherit
the setting.

## Regenerating

From the repository root, into an empty directory:

```sh
dotnet run --project tools/RegressionFixtures5021 -- WalCrash /tmp/fixtures/WalCrash
```

The subcommands are `WalCrash`, `EncryptedWalCrash`, `ConcurrentWalCrash` and `ForeignWal`. The
`_5_0_21` suffix and `.zip` are also accepted. Each run writes exactly the entries of that
fixture and prints the SHA-256 of each file. It also prints what the package reads back. Reads
that were part of the original recipe run on the fixture file; all other checks run on copies
in a temporary directory, which also holds the scratch files.

The pinned archives were made with Python, with the entries in the order listed below:

```sh
python3 -c "import zipfile; z = zipfile.ZipFile('WalCrash_5_0_21.zip', 'w', zipfile.ZIP_DEFLATED); z.write('crash.db'); z.write('crash-log.db'); z.close()"
```

`ConcurrentWalCrash_5_0_21.zip` alone was made with Info-ZIP (`zip -q ... c.db c-log.db`).

5.0.21 draws skip-list node levels from a fixed-seed randomizer that lives for the whole
process. The originals ran several steps as separate processes, so the generator runs those
steps as child processes too. This lets index pages match. Reordering or merging steps changes
the index pages but not what the file contains.

A regenerated archive gets a new hash. Publishing it means adding it to LiteDB-Artifacts and
pinning the new revision and hash in `Resources/artifacts.json` in the same change.

### What a regeneration reproduces

Regenerated bytes differ from the pinned ones. They are not expected to match:

- **Header creation time.** 5.0.21 stores the creation time in header bytes 68..75, and a WAL
  carries it in every header page it commits.
- **Encryption.** Encrypted files get a new random salt, so every encrypted byte differs.
- **Crash timing.** The images depend on when the files were copied or the process died.
- **ZIP metadata.** Timestamps and compression output differ.

What must match is the logical content. That means the same entry names and page counts, the
same collections, documents, index names and expressions, and the same pragmas. Crash images
must hold the same WAL transactions and confirmation pages, and each fixture must produce the
consumer outcome listed below.

Verified on 2026-09-28 with the generator run on .NET 8.0.31:

| Fixture | Regenerated compared with pinned |
| --- | --- |
| WalCrash | `crash-log.db` byte-identical; `crash.db` differs only in the creation time |
| EncryptedWalCrash | salt and ciphertext differ; decrypted (AES-256-ECB, PBKDF2-SHA1 key) every page is identical except the creation time |
| ConcurrentWalCrash | `c.db` differs only in the creation time; `c-log.db` has the same 13 pages (transactions 2 to 4, committed pages 58 and 59) and differs only in the creation time of its two header pages |
| ForeignWal | same 4 pages (collection, data, index, confirmed header with LastPageID 1732); differs only in the header's creation time |

With the regenerated entries zipped in place of the pinned ones, the consuming test classes
passed (`net10.0`, Release, `TestingEnabled`), as they did with the pinned files.
ConcurrentWalCrash was also regenerated on .NET 10.0.12 with the same result.

The pinned headers also corroborate their provenance. Each one's creation time lies within
seconds of its recorded generator run; for example, the time in `crash.db` of WalCrash is
2026-09-27 23:30:31.

## Fixtures

### WalCrash_5_0_21.zip (`e8785c4d6`)

`crash.db` and `crash-log.db` are a process-crash image with committed WAL transactions.
The program opened `Filename=<path>` (direct connection, no password, default pragmas). It
indexed `value` in collection `docs`, inserted `{_id: 0..99, value: 0}` and checkpointed. It
then updated `_id` 0..19 to `value: 7` and inserted `{_id: 100, value: 7}`; these commits
exist only in the WAL. The same process copied both files while the engine held them open,
then exited with `Environment.Exit(0)` without disposing. No bytes were changed afterwards.
5.0.21 recovers 101 documents, 21 of them with value 7.

The current engine is expected to behave as follows:

- A writable open converts the file and keeps every commit (101 and 21).
- `ReadOnly=true;Legacy Index Scan=true` reads the same without writing.
- While a shared reader holds a snapshot, or the shared reader registry cannot be inspected,
  the conversion is refused with `LOCK_TIMEOUT` and both files stay byte for byte; it converts
  once the reader is gone.
- With a committed page appended that is beyond both files, or is not a page, the open fails
  with `INVALID_DATABASE` (103) and changes neither file.
- With a torn tail appended to its WAL, the conversion keeps every commit.

Consumers: `LegacyWalSharedMigration_Tests`, `LegacyWalTornTail_Tests`,
`LegacyWalPageBound_Tests` (also as the data file beside ForeignWal),
`scripts/test-5021-regression-compatibility.py`, and the ReproRunner proofs
`Issue_3027_LegacyWalConversion` and `Issue_3027_ForeignLegacyWal`. It is retained as the real
5.0.21 WAL that the legacy conversion must drain.

### EncryptedWalCrash_5_0_21.zip (`5873fde3c`)

`crash.db` and `crash-log.db` form an encrypted process-crash image. The program used
`Password=wal-secret` and `Pragma("CHECKPOINT", 0)`. It indexed `value` in `docs`, inserted
`{_id: 0..59, value: 0}` and checkpointed. It then updated 0..9 to value 7 and inserted
`{_id: 60..64, value: 7}`, which exist in the WAL only. Both files were copied while the engine
held them open, and then the engine was disposed. Nothing was patched. 5.0.21 recovers 65
documents, 15 with value 7.

The current engine is expected to convert the file on a writable open with the password, also
with a torn tail of 16 or 100 bytes appended, and to read 65 and 15 twice. Consumer:
`LegacyWalTornTail_Tests`. It is retained for the encrypted legacy WAL, whose torn tail is not
a whole AES block.

### ConcurrentWalCrash_5_0_21.zip (`3c502e92f`)

`c.db` and `c-log.db` were made by a reviewer's program in two processes, both with
`Connection=direct`.

1. The first process wrote collections `a` and `b` with 10 documents each and closed.
2. In the second, a worker thread opened an explicit transaction on `a` with 300 inserts of
   1,000 characters, which took page IDs 7..57 without writing them. The main thread committed 3
   inserts of 6,000 characters into `b` (new pages 58 and 59). After 2 s the process killed
   itself with `Environment.FailFast`.

Nothing was patched. The data file has 7 pages (LastPageID 6); the WAL has 13 pages whose
committed headers raise LastPageID to 58 and 59. 5.0.21 reopens it with a=10 and b=13.

The current engine is expected to accept these legitimate committed pages above the data file's
LastPageID. Writable and read-only (legacy index scan) opens read b=13 (3 with `_id` >= 100)
and a=10. Consumers: `LegacyWalPageBound_Tests`, `scripts/test-5021-regression-compatibility.py`.

### ForeignWal_5_0_21.zip (`3b8744cdf`)

`foreign-log.db` is the WAL of another database. The reviewer's program inserted 10,000
documents of 1,000 characters into `big` and closed. It reopened with `Connection=direct`,
inserted `{_id: 1, v: "foreign"}` into a new collection `fresh` (committed with its header,
LastPageID 1732), slept 2 s and called `Environment.FailFast`. Only the WAL is kept; the 14 MB
data file is discarded. Nothing was patched.

The foreign pairing is made by the tests: they place this WAL beside WalCrash's `crash.db`,
whose creation time differs.

The current engine is expected to refuse every open with `INVALID_DATABASE` (103), "commits the
header of another database": default, read-only legacy scan, and `Auto-Rebuild=true`. Neither
file changes. Its header page (WAL page 3), with LastPageID raised to cover a far page, is
refused the same way. Consumers: `LegacyWalPageBound_Tests`,
`scripts/test-5021-regression-compatibility.py` and the ReproRunner proof
`Issue_3027_ForeignLegacyWal`.

## Provenance limits

Each file was written by the package named in its archive. The tests depend on these points:

- **The crash images are not power cuts.** WalCrash and EncryptedWalCrash are copies the writer
  process made of its own open files. ConcurrentWalCrash and ForeignWal are left by a process
  that died.
- **ForeignWal is a real 5.0.21 WAL, but a pairing made by the tests:** it is placed beside
  another database's data file.
- **ConcurrentWalCrash and ForeignWal came from a reviewer's program in the same session**, which
  also ran the 5.0.21 package.
