# Regression fixtures written by released LiteDB packages

The fixtures below were written for PR #3027 (IO regressions since 5.0.21) by the published
LiteDB 5.0.21 and 6.0.0-prerelease.114 NuGet packages, not by this repository's engine. The
tests that read them assert how the current engine reads, migrates or refuses real files of
those versions. This file records, per issue #3034 §5, the producer, the generator, the runtime,
the configuration, any bytes changed afterwards, the committed hashes, the expected outcome and
why each fixture is kept.

The generators were rebuilt from the recorded commands of the session that made the fixtures
(the original scratch programs were not kept):

- `tools/RegressionFixtures5021`: every `*_5_0_21.zip`, one subcommand per fixture.
- `tools/PrereleaseVectorFixture`: the entries of `Vectors_6_0_0_prerelease_114.zip`.

## Environment

All files were written on 2026-09-27/28 (UTC) on Linux x64: Ubuntu 24.04.4 LTS, kernel 6.18.44,
ext4. The .NET SDK was 10.0.401 with runtimes 10.0.12 and 8.0.31. `LANG` was unset, so the
current culture was the invariant culture and 5.0.21 stored collation LCID 127 with IgnoreCase
in every header. Both generators pin the invariant culture, so any host writes the same
collation.

The original programs targeted two frameworks, which decided the runtime:

| Runtime | Fixtures |
| --- | --- |
| .NET 10.0.12 (`net10.0`, Release) | WalCrash, DropIndex, DamagedDocument, DamagedUniqueDocuments, DamagedIndexKeys, EncryptedWalCrash |
| .NET 8.0.31 (`net8.0`) | ConcurrentWalCrash, ForeignWal, DamagedSalvageDuplicate, Vectors (vectors.db and vectors-encrypted.db from a Debug build) |

Both runtimes load the same package assembly. The generators target `net8.0`. To run them on
.NET 10 as the first group was, set `DOTNET_ROLL_FORWARD=LatestMajor`. Child processes inherit
the setting.

## Regenerating

From the repository root, into an empty directory:

```sh
dotnet run --project tools/RegressionFixtures5021 -- WalCrash /tmp/fixtures/WalCrash
DOTNET_ROLL_FORWARD=LatestMajor dotnet run --project tools/RegressionFixtures5021 -- DropIndex /tmp/fixtures/DropIndex
dotnet run --project tools/PrereleaseVectorFixture -- /tmp/fixtures/Vectors
```

The subcommands are `WalCrash`, `EncryptedWalCrash`, `ConcurrentWalCrash`, `ForeignWal`,
`DropIndex`, `DamagedDocument`, `DamagedUniqueDocuments`, `DamagedIndexKeys` and
`DamagedSalvageDuplicate`. The `_5_0_21` suffix and `.zip` are also accepted. Each run writes
exactly the entries of that fixture and prints the SHA-256 of each file. It also prints what the
package reads back. Reads that were part of the original recipe run on the fixture file; all
other checks run on copies in a temporary directory, which also holds the scratch files.

The committed archives were made with Python, with the entries in the order listed below:

```sh
python3 -c "import zipfile; z = zipfile.ZipFile('WalCrash_5_0_21.zip', 'w', zipfile.ZIP_DEFLATED); z.write('crash.db'); z.write('crash-log.db'); z.close()"
```

`ConcurrentWalCrash_5_0_21.zip` alone was made with Info-ZIP (`zip -q ... c.db c-log.db`).

5.0.21 draws skip-list node levels from a fixed-seed randomizer that lives for the whole
process. The originals ran several steps as separate processes, so the generators run those
steps as child processes too. This lets index pages match. Reordering or merging steps changes
the index pages but not what the file contains.

### What a regeneration reproduces

Regenerated bytes differ from the committed ones. They are not expected to match:

- **Header creation time.** 5.0.21 stores the creation time in header bytes 68..75, and a WAL
  carries it in every header page it commits.
- **Encryption.** Encrypted files get a new random salt, so every encrypted byte differs.
- **Vector-index pages (prerelease.114 only).** `VectorIndexService` draws node levels from an
  unseeded `new Random()`.
- **Crash timing.** The images depend on when the files were copied or the process died.
- **ZIP metadata.** Timestamps and compression output differ.

What must match is the logical content. That means the same entry names and page counts, the
same collections, documents, index names and expressions, and the same pragmas. Crash images
must hold the same WAL transactions and confirmation pages, damaged files the same unreadable
values, and each fixture must produce the consumer outcome listed below.

Verified on 2026-09-28 with the generators run on .NET 8.0.31:

| Fixture | Regenerated compared with committed |
| --- | --- |
| WalCrash | `crash-log.db` byte-identical; `crash.db` differs only in the creation time |
| DropIndex | each file differs only in the creation time |
| DamagedDocument, DamagedUniqueDocuments, DamagedIndexKeys, DamagedSalvageDuplicate | differs only in the creation time (the damage is at the same offsets) |
| EncryptedWalCrash | salt and ciphertext differ; decrypted (AES-256-ECB, PBKDF2-SHA1 key) every page is identical except the creation time |
| ConcurrentWalCrash | `c.db` differs only in the creation time; `c-log.db` has the same 13 pages (transactions 2 to 4, committed pages 58 and 59) and differs only in the creation time of its two header pages |
| ForeignWal | same 4 pages (collection, data, index, confirmed header with LastPageID 1732); differs only in the header's creation time |
| Vectors | plain files differ in the creation time, in the vector pages (page type 5) and in one byte of vector metadata on each collection page; data and skip-list index pages are identical; read with prerelease.114, all three files (the encrypted one too) hold the same documents, index definitions and nearest-neighbour results, and document 2 of `vector-salvage.db` is still unreadable |

With the regenerated entries zipped in place of the committed ones, the 98 tests of the eleven
consuming classes passed (`net10.0`, Release, `TestingEnabled`), as they did with the committed
files. DamagedDocument and ConcurrentWalCrash were also regenerated on .NET 10.0.12 with the same
result.

The committed headers also corroborate their provenance. Each one's creation time lies within
seconds of its recorded generator run; for example, the time in `crash.db` of WalCrash is
2026-09-27 23:30:31.

## Fixtures

### WalCrash_5_0_21.zip (`e8785c4d6`)

`crash.db` and `crash-log.db` are a process-crash image with committed WAL transactions.
The program opened `Filename=<path>` (direct connection, no password, default pragmas). It
indexed `value` in collection `docs`, inserted `{_id: 0..99, value: 0}` and checkpointed. It
then updated `_id` 0..19 to `value: 7` and inserted `{_id: 100, value: 7}`; these commits
exist only in the WAL. The same process copied both files while the engine held them open,
then exited with `Environment.Exit(0)` without disposing. No bytes were changed afterwards.
5.0.21 recovers 101 documents, 21 of them with value 7.

The current engine is expected to behave as follows:

- A writable open converts the file and keeps every commit (101 and 21).
- `ReadOnly=true;Legacy Index Scan=true` reads the same without writing.
- Storage that cannot sync refuses the conversion with an `IOException` ("Cannot convert this
  legacy database now"), leaving both files byte for byte.
- With a committed page appended that is beyond both files, or is not a page, the open fails
  with `INVALID_DATABASE` (103) and changes neither file.

Consumers: `LegacyWalSharedMigration_Tests`, `LegacyWalTornTail_Tests`,
`LegacyWalPageBound_Tests` (also as the data file beside ForeignWal), `UnsyncableDataFile_Tests`,
`DataFileStopsSyncing_Tests` and `UnsyncedBackfillPowerLoss_Tests`. It is retained as the real
5.0.21 WAL that the legacy conversion must drain.

### DropIndex_5_0_21.zip (`e8785c4d6`, items added in `ac2a81f48`)

Three files, each written by one process with `new LiteDatabase(path)` and closed normally.
Nothing was patched.

- **`customers.db`:** collection `customers` with indexes Name, Age and CustomerId, 200
  documents `{_id: i, Name: "n"+i, Age: i%90, CustomerId: "C"+i}`, then `DropIndex("Age")`.
- **`items-a.db`:** collection `items` with 50 documents `{_id: i, <field>: <field>+i}`. It had
  indexes on CreatedAt, Phone and Status, then dropped CreatedAt and Phone.
- **`items-b.db`:** the same collection shape with indexes on LastLogin, Score, CustomerId,
  Country and Status, then dropped CustomerId, LastLogin, Country and Score.

The two `items` layouts are two of 40 seeded random layouts; they are the two that failed.
5.0.21 leaves the tail of the old index list on the collection page, and itself keeps
inserting, updating, deleting and indexing in all three files.

The current engine is expected to behave as follows:

- A writable open migrates each file, and the collection stays writable.
- Every interrupted-migration image recovers writable.
- A vector index added later keeps its metadata.
- A non-writable stream opens read-only without migrating, and the file stays unchanged.

Consumers: `LegacyDroppedIndex_Tests`, `LegacyReadOnlyStream_Tests` and
`ReadOnlyStorageEngine_Tests`. It is retained because the stale tail was once read as vector
metadata, which failed every insert after migration.

### DamagedDocument_5_0_21.zip (`e8785c4d6`)

`damaged.db` holds collection `c` with `{_id: 1..3, a: "keep-i", b: "tail-i-" + 20 × "z"}`, then
closed. Post-processing: the same program then overwrote the BSON length of string `b` of
document 2 (file offset 24,713) with `0x7FFFFFF0`. This models damage inside one document.
5.0.21 opens the file, reads documents 1 and 3, fails on document 2
(`ArgumentOutOfRangeException`), and its `Rebuild()` keeps `{_id: 2, a: "keep-2"}`.

The current engine is expected to behave as follows:

- The default writable open fails with `INVALID_DATAFILE_STATE` (999). The error names
  collection `c` and the remedies, and only header byte 191 (the rebuild mark) changes.
- `Auto-Rebuild=true` keeps documents 1 and 3, keeps the readable part of document 2, and
  records it in `_rebuild_errors`.
- A read-only open or a read-only stream reads document 1 and reports the damage when a scan
  reaches document 2, changing nothing.

Consumers: `LegacyDamagedDocument_Tests` and `ReadOnlyStorageEngine_Tests`.

### DamagedUniqueDocuments_5_0_21.zip (`62d8f602f`)

`damaged.db` holds collection `c` with a unique index on `b` and `{_id: 1..4, a: "keep-i",
b: "u-i"}`, checkpointed and closed. Post-processing: the BSON length of `a` in documents 2 and
3 was overwritten with `0x7FFFFFF0`, so only their `_id` is readable. 5.0.21 then opened the
file and ran `FindById` 1, 4 and 2 (the last fails) before the file was kept; that open wrote
nothing. 5.0.21's own `Rebuild()` fails with "Cannot insert duplicate key in unique index 'b'.
The duplicate value is 'null'."

The current engine, under `Auto-Rebuild=true`, is expected to keep 1, the readable part
`{_id: 2}` and 4. It reports document 3, whose null key would repeat in the unique index, and
the index stays unique. Consumer: `LegacyDamagedDocument_Tests`.

### DamagedIndexKeys_5_0_21.zip (`c8d02b00a`, replaced in `d5a30871c`)

`damaged.db` holds collections `maxed`, `mined`, `long` and `throws`. Each has `{_id: 1..3,
a: "keep-i", b: "u-i"}` and an index `k` on, respectively:

- `COALESCE($.b, MAXVALUE())`
- `COALESCE($.b, MINVALUE())`
- `COALESCE($.b, <1,100 × "k">)`
- `SUBSTRING(COALESCE($.b, 'x'), 1, 2)`

The file was checkpointed and closed. Post-processing: the length of `b` of document 2 was
overwritten in every collection (4 places). 5.0.21 then opened it and read documents 1 and 3 of
each collection before the file was kept. The first commit held a separate three-collection run
without `mined`. `d5a30871c` replaced it with this four-collection run.

The current engine is expected to behave as follows, with header byte 191 set to 1 in the test
and `Auto-Rebuild=true`:

- Each collection keeps documents 1 and 3 and its index `k`.
- Document 2 is reported: for `maxed`, `mined` and `long` its key is not valid; for `throws` its
  keys cannot be computed.

Consumer: `LegacyDamagedDocument_Tests`.

### DamagedSalvageDuplicate_5_0_21.zip (`68931ef4f`)

`damaged.db` was written with `Connection=direct`: collection `c`, a unique index on `$.b`, and
the documents `{_id: 1, a: "keep-1", b: "u-1"}`, `{_id: 7, b: "u-7", a: "tail-7"}`,
`{_id: 8, a: "keep-8", b: "u-8"}` and `{_id: 9, a: "keep-9", b: "u-9"}`. 5.0.21 read them back
read-only, then the process exited.

Post-processing was done by a Python script, ported unchanged to the generator. Each pattern is
required to occur exactly once:

- The stored `b` of document 7 became `"u-1"`.
- The stored `_id` of document 8 became 7.
- The length of `a` in both documents became `0x7FFFFFF0`.

Only the document bytes were changed; the `_id` and `b` index nodes still hold 7, 8, "u-7" and
"u-8". 5.0.21 itself could not write this state.

The current engine, under `Auto-Rebuild=true`, is expected to keep 1, `{_id: 7}` (the second
readable part) and 9. It reports the first readable part, whose "u-1" repeats a unique key,
and reports no "same _id" error. Consumer: `LegacyDamagedDocument_Tests`.

### EncryptedWalCrash_5_0_21.zip (`5873fde3c`)

`crash.db` and `crash-log.db` form an encrypted process-crash image. The program used
`Password=wal-secret` and `Pragma("CHECKPOINT", 0)`. It indexed `value` in `docs`, inserted
`{_id: 0..59, value: 0}` and checkpointed. It then updated 0..9 to value 7 and inserted
`{_id: 60..64, value: 7}`, which exist in the WAL only. Both files were copied while the engine
held them open, and then the engine was disposed. Nothing was patched. 5.0.21 recovers 65
documents, 15 with value 7.

The current engine is expected to convert the file on a writable open with the password, also
with a torn tail of 16 or 100 bytes appended, and to read 65 and 15 twice. Consumer:
`LegacyWalTornTail_Tests`. It is retained for the encrypted legacy WAL, whose torn tail is not
a whole AES block.

### ConcurrentWalCrash_5_0_21.zip (`3c502e92f`)

`c.db` and `c-log.db` were made by a reviewer's program in two processes, both with
`Connection=direct`.

1. The first process wrote collections `a` and `b` with 10 documents each and closed.
2. In the second, a worker thread opened an explicit transaction on `a` with 300 inserts of
   1,000 characters, which took page IDs 7..57 without writing them. The main thread committed 3
   inserts of 6,000 characters into `b` (new pages 58 and 59). After 2 s the process killed
   itself with `Environment.FailFast`.

Nothing was patched. The data file has 7 pages (LastPageID 6); the WAL has 13 pages whose
committed headers raise LastPageID to 58 and 59. 5.0.21 reopens it with a=10 and b=13.

The current engine is expected to accept these legitimate committed pages above the data file's
LastPageID. Writable and read-only (legacy index scan) opens read b=13 (3 with `_id` >= 100)
and a=10. Consumer: `LegacyWalPageBound_Tests`.

### ForeignWal_5_0_21.zip (`3b8744cdf`)

`foreign-log.db` is the WAL of another database. The reviewer's program inserted 10,000
documents of 1,000 characters into `big` and closed. It reopened with `Connection=direct`,
inserted `{_id: 1, v: "foreign"}` into a new collection `fresh` (committed with its header,
LastPageID 1732), slept 2 s and called `Environment.FailFast`. Only the WAL is kept; the 14 MB
data file is discarded. Nothing was patched.

The foreign pairing is made by the tests: they place this WAL beside WalCrash's `crash.db`,
whose creation time differs.

The current engine is expected to refuse every open with `INVALID_DATABASE` (103), "commits the
header of another database": default, read-only legacy scan, and `Auto-Rebuild=true`. Neither
file changes. Its header page (WAL page 3), with LastPageID raised to cover a far page, is
refused the same way. Consumer: `LegacyWalPageBound_Tests`.

### Vectors_6_0_0_prerelease_114.zip (`cf92a407d`, `vector-salvage.db` added in `e94c95b1a`)

The prerelease stores vector indexes in FILE_VERSION 8 files, with a vector section after a
collection page's index list.

- **`vectors.db` and `vectors-encrypted.db`:** written with no password and with
  `Password=vector-secret`. Collection `docs` holds `{_id: 1..40, name: "d"+i, Embedding: [i, 1]}`
  with index `name` and vector index `embedding` on `$.Embedding` (2 dimensions). Collection
  `computed` holds `{_id: 1..20, Embedding: [1, i]}`, with every fifth Embedding null, and
  vector index `coalesced` on `COALESCE($.Embedding, [0, 0])`. Nothing was patched.
- **`vector-salvage.db`:** written in a later process. Collection `vectors` holds `{_id: 1..3,
  a: "keep-i", b: "u-i", v: [i, 1]}` with vector index `vv` on
  `IIF(SUBSTRING(COALESCE($.b, 'x'), 1, 2) = '-0', $.v, $.v)`, checkpointed and closed.
  Post-processing: the same program overwrote the length of `b` in document 2 with `0x7FFFFFF0`.

`e94c95b1a` rebuilt the archive with the unchanged first two entries plus `vector-salvage.db`.

The current engine is expected to behave as follows:

- A writable open migrates `vectors.db` and `vectors-encrypted.db`, and their vector indexes stay
  usable.
- Rebuild and auto-rebuild keep those indexes with no `_rebuild_errors`.
- In-test copies with a rewritten index list report the vector index instead of throwing.
- For `vector-salvage.db`, `Auto-Rebuild=true` keeps documents 1 and 3 and the vector index `vv`,
  and reports document 2 because its vector value cannot be computed.

Consumer: `PrereleaseVectorFile_Tests`.

## Provenance limits

Each base file was written by the package named in its archive. Several files were then changed
or combined; the tests depend on each of these points:

- **Five files were byte-patched after the package closed them:** `damaged.db` of the four
  `Damaged*` archives and `vector-salvage.db`. All damage is a BSON string length set to
  `0x7FFFFFF0`. DamagedSalvageDuplicate also rewrites two stored values, so its documents
  disagree with their index nodes.
- **The crash images are not power cuts.** WalCrash and EncryptedWalCrash are copies the writer
  process made of its own open files. ConcurrentWalCrash and ForeignWal are left by a process
  that died.
- **ForeignWal is a real 5.0.21 WAL, but a pairing made by the tests:** it is placed beside
  another database's data file.
- **ConcurrentWalCrash and ForeignWal came from a reviewer's program in the same session**, which
  also ran the 5.0.21 package.
