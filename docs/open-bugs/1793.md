# Issue 1793: large integral JSON tokens overflow Int32 parsing

Source: https://github.com/litedb-org/LiteDB/issues/1793 (open on 2026-09-13;
all seven comments reviewed; no attached assets).

## Reproduction status

**NO REPRO on current dev: the reported behavior is already correct.** The
reported `{ "LargeDouble": 210000000000 }` input no longer throws
`OverflowException`. Current `JsonReader` first attempts `Int32`, then parses a
bare integral token outside that range as `Int64`. That behavior was introduced
by historical commit `cd1f67fee877269a74f1716d8928355561a16b30` and received a
broad test in `086a6e0f30d12ba01bbbcec0ef68ac352c82bc1b`.

The issue began by suggesting that an integer-shaped token be treated as
`Double`, because its producer had omitted the decimal point. In the comments,
the LiteDB contributor proposed `Int64` instead and the reporter explicitly
agreed that it made more sense. JSON cannot preserve the producer's unstated
CLR type, so the regression protects the agreed syntax-based contract:

- bare integral tokens inside the signed Int32 range are `BsonType.Int32`;
- bare integral tokens outside Int32 but inside signed Int64 are exact
  `BsonType.Int64` values; and
- a token with an explicit decimal marker remains `BsonType.Double`.

It does not claim that a bare `210000000000` can be identified as the Double
that the original application intended.

## Independent anti-green checks

`Issue1793_Tests` covers both Int32 boundaries, the immediately adjacent Int64
values, the issue's positive and negative sample, both signed Int64 extrema,
and positive/negative `9007199254740993`. The last value is one beyond Double's
exact-integer range, so silently coercing all large tokens to Double cannot pass.

Each large value is checked through `BsonType`, the runtime type of `RawValue`,
and its exact `AsInt64` value. Distinct fields before and after the number must
also survive with the expected count and types, preventing an implementation
from ignoring the offending field or truncating the document. Serialization
must emit the exact value through `$numberLong`, and reparsing must retain its
Int64 type and exact value. A paired `210000000000.0` control must remain
Double. These checks strengthen the older test: `BsonValue` equality compares
different numeric types after conversion, so its exactly representable
`210000000000` case alone could remain green after Int64-to-Double coercion.
