# Issue 2059: [BUG] DB get operation fails with LiteDB ENSURE: invalid segment position

Source: https://github.com/litedb-org/LiteDB/issues/2059 (open on 2026-09-13).

## Reproduction status

**Originating bug not reproduced.** The report concerns a previously existing, corrupted
database made by LiteDB 5.0.10 on Windows 7/.NET 4.6. The reporter privately transferred
the data file in 2021, but it is not attached to the issue and is no longer available.
The report does not contain the operation or interruption that damaged the page.

The query is where the damaged footer was detected, not evidence that the query created
the damage. Manually damaging a page or truncating a WAL can manufacture the same
`invalid segment position` symptom, but that is only a symptom fixture/candidate failure
mechanism. It must not be presented as a reproduction of the customer's corruption.

## Healthy control and independent checks

`Issue2059_Tests` follows the public portion of the report: one file-backed
`SimpleRecord` collection, an `InvNum` index, all three supplied invoice numbers, and the
exact `InvNum && !Zastareo && !CisError` predicate followed by the newest `SendDateTime`.
It adds bounded variable-size insert/update/delete churn, checkpoints, and repeated opens.

The test does not merely assert that no exception was thrown. An external ledger is
reconciled against every persisted field of every record after each round; the reported
queries must return the exact independently expected records; the query plan must use the
`InvNum` index; the selected newest record must match the ledger; the data file must span
many complete pages; and query-only reopens must leave its bytes unchanged. These checks
prevent a purported fix from going green by swallowing the exception, dropping damaged
records, returning partial results, bypassing the reported index path, or rewriting data
during a read.
