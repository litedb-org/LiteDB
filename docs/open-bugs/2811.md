# Issue 2811: Insert with auto-id throws NullReferenceException after writing the document when the Id member has no setter (get-only property, F# record)

Source: https://github.com/litedb-org/LiteDB/issues/2811 (open on 2026-09-12).

## Observed on dev

Base: `789d57d80cd44ec28ae6a532b4079daeeba9e755`; Release, .NET 8, Linux.
`8` failed, `0` passed. Assertions describe correct behavior; failures are not skipped or inverted.

## Executed cases

- Failed for both `int` and `ObjectId`: `Insert(T)`, `Insert(IEnumerable<T>)`,
  `Upsert(T)`, and `Upsert(IEnumerable<T>)` all throw `NullReferenceException`
  instead of either completing or reporting the read-only `Id` member.
- The direct `Insert(T)` cases additionally leave the target durably present after
  throwing. A fresh connection sees it and the database bytes differ from the
  checkpointed baseline. The enumerable and upsert paths currently roll back,
  but still expose the same null dereference.
- The tests independently verify immediate and reopened raw BSON ledgers,
  generated-ID type/uniqueness and write results. A rejection must name `Id` and
  explain the missing setter/read-only member, retain the exact control ledger,
  and leave the checkpointed database bytes identical. This prevents a
  write-then-delete compensation from satisfying the atomicity contract.

Run: `dotnet test LiteDB.Tests -c Release -f net8.0 -p:TestingEnabled=true --settings tests.runsettings --filter FullyQualifiedName~Issue2811_`.
