# Issue 2819: Unindexed OrderBy throws NotImplementedException when a string or binary sort key is longer than 255 bytes

Source: https://github.com/litedb-org/LiteDB/issues/2819 (open on 2026-09-12).

## Observed on dev

Base: `4eca573513de1e7e95fa72b74a954fb179eb728f`; Release, .NET 8, Linux.
12 failed and 4 passed. Assertions describe correct behavior; failures are not skipped or inverted.

## Executed cases

- Passed: both 255-byte string/binary cases in `Extended_unindexed_sort_keys_preserve_the_entire_key`.
- Failed: all six 256-, 300-, and 1000-byte string/binary cases in that theory with `NotImplementedException`. The compared keys share their prefix and differ near the end, so a reader that truncates long keys cannot satisfy the order ledger.
- Failed: both string/binary `Maximum_legal_unindexed_key_preserves_its_last_bytes` cases with `NotImplementedException`. Each payload is independently fixed at 1021 bytes, for the documented maximum 1023-byte serialized key.
- Failed: both string/binary `Clearly_oversized_unindexed_key_reports_the_sort_key_contract` cases. Dev throws `ArgumentOutOfRangeException (length)` for a 1100-byte payload instead of `LiteException` code 111 and `Sort key must be less than 1023 bytes.`
- Passed: both string/binary `Extended_indexed_key_uses_the_named_index_in_an_independent_control` cases. The execution plan names the `key` index and the full 300-byte values and payloads sort correctly; these controls execute even while the unindexed cases fail.
- Failed: both string/binary `Unindexed_extended_keys_are_merged_from_multiple_sort_containers` cases with `NotImplementedException`. Each case supplies 2,800 entries / 859,600 serialized sort bytes, exceeding the source-defined 819,200-byte container. The plan proves `key` is unindexed, and the success oracle verifies every independently derived ID, rank, payload, and key plus at least two full containers written to the caller-owned temp stream.
