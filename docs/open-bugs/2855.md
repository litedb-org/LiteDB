# Issue 2855: `Upgrade=true` is ignored for stream databases

Source: https://github.com/litedb-org/LiteDB/issues/2855

The issue was open with no comments when checked on 2026-09-13. Its source is
the still-open PR [#1969](https://github.com/litedb-org/LiteDB/pull/1969), whose
single commit `42d8d92a54418fdb90a22d91f5e57eeff8405d50` added a stream upgrade API
and a `MemoryStream` test in 2021. The old patch no longer applies directly to
dev because dev now routes file upgrades through `Recovery` and
`RebuildService`.

## Current-dev result

The regression is executable and fails on current dev. The .NET 8 run reports
four expected failures:

```text
Upgrade_true_converts_v4_data_stream_and_preserves_the_full_ledger  FAIL
  LiteException: File is not a valid LiteDB database format or contains a invalid password.
Stream_constructor_exposes_and_honours_an_upgrade_option             FAIL
  Expected constructor not to be <null>.
Upgrade_true_rejects_a_read_only_v4_stream_without_changing_it       FAIL
  Invalid-database message does not explain that writing is required.
Upgrade_true_rejects_a_non_seekable_v4_stream_without_changing_it    FAIL
  The propagated stream error does not explain that seeking is required.

Failed: 4, Passed: 0, Total: 4
```

The first failure is the core bug. `LiteEngine.Open` observes `Upgrade=true`,
but `TryUpgrade` only reads `EngineSettings.Filename`. With `DataStream` set,
`Filename` is null, `File.Exists(null)` is false, and upgrade returns without
examining or replacing the stream. Normal v8 header parsing then rejects the
unchanged v4 bytes. `LiteDatabase(Stream, BsonMapper, Stream)` also has no
upgrade parameter.

## Why the test is hard to fake green

`Issue2855_Tests` copies the repository's real `LiteDB.Tests/Resources/v4.db`
into an expandable, writable, seekable `MemoryStream`. Before invoking LiteDB,
it independently pins all of these source facts:

- length `73728` and SHA-256
  `af6864cf7ba5a3f836b34ea736934e5d7a38e78071eeba30ef58c0c61f9b7348`;
- the v7 marker at byte 25 and format byte `7` at byte 52;
- a deliberately nonzero initial stream position, so detection must seek to
  the header rather than depend on caller position.

A successful upgrade must then satisfy both sides of the ledger:

- raw persisted bytes have the v8 marker at byte 32, format byte `8` at byte
  59, an 8192-byte page-aligned length, and differ from the v4 source;
- all five original collections, all seven original domain documents, all six
  index definitions, the nested customer, and its indexed lookup remain exact;
- the migrated FileStorage record and its structured v5 chunk id expose the
  exact 77-byte payload, filename, MIME type, timestamp, and metadata;
- a new probe document is checkpointed after migration and survives reopen;
- reopening the already-upgraded stream again with `Upgrade=true` preserves
  the complete ledger and leaves every datafile byte unchanged.

These checks prevent fixes that merely skip the format error, rewrite only the
header, drop difficult collections/indexes/chunks, keep converted data only in
memory, or rebuild an already-current database on every open.

The constructor test locates a stream constructor with a Boolean parameter
named `upgrade` through reflection, invokes it on the same real v4 fixture, and
requires the same semantic and raw result. Reflection keeps the regression
compilable before that requested API exists while still protecting the API and
its behavior. Separate read-only and non-seekable cases require an explanatory
error and byte-for-byte preservation of the rejected source.

## Satisfiability check

To ensure the assertions describe a feasible repair rather than an impossible
output, an isolated disposable archive was given a minimal reference repair:

- detect v7 on `EngineSettings.DataStream`, validate read/seek/write support,
  rebuild through `FileReaderV7` into a temporary `MemoryStream`, then truncate
  and replace the caller's stream;
- add a Boolean `upgrade` option to the stream constructor and forward it into
  `EngineSettings.Upgrade`.

No repair source was retained in the worktree. Running the same focused .NET 8
command in that isolated copy passed all four tests (`0 failed, 4 passed`) in
163 ms. A real fix may use a different implementation, but it must preserve the
same persisted-format, semantic, mutation, idempotence, API, and rejection
contracts.
