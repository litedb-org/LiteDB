# Issue 2826: v7 upgrade trusts broken extend-page links

Source: https://github.com/litedb-org/LiteDB/issues/2826 (open on
2026-09-14).

## Observed on dev

`Issue_2826_BrokenV7PageLinks` reproduces with package 5.0.21 and current
`dev`. Both variants exit `0` with `BUG_2826_CONFIRMED`.

The self-looping extend page reaches the bounded managed-heap limit and throws
`OutOfMemoryException`. The link one page beyond EOF throws
`NullReferenceException` from `FileReaderV7`. The byte-identical healthy v7
control upgrades successfully and preserves both documents after reopen.

## Double-entry checks

- The committed v4.1.4 fixture has a pinned size and SHA-256. A raw parser—not
  LiteDB—proves its header, page ownership, index-to-data references, complete
  five-page extend chain, and exact BSON payloads.
- Each corrupt copy differs only in the first extend page's four-byte
  `NextPageID`: one self-loop and one provably past-EOF value.
- Separate bounded child processes cap time, managed heap, and working set. A
  timeout or memory breach counts only after an upgrade-start marker, confirmed
  process-tree termination, and complete output capture.
- An exception is a fix only when it is a `LiteException` and the database plus
  every directory sidecar remains byte-for-byte unchanged.
- A recovery-style fix must preserve the exact intact row, invent no rows,
  preserve any recovered large row exactly, and persist a nonempty error ledger
  identifying the damaged page chain.
- Both malformed link shapes must pass the safe contract. An arbitrary crash,
  swallowed exception, fixture failure, or one-shape special case is exit `20`,
  not a false green.
