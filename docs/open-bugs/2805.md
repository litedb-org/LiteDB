# Issue 2805: EnsureIndex auto-names are empty or culture-dependent

Source: https://github.com/litedb-org/LiteDB/issues/2805 (open on 2026-09-14).

## Observed on dev

Branch head: `4eca573513de1e7e95fa72b74a954fb179eb728f`; Release, .NET 8, Linux.
All five assertions describe the required behavior; none is skipped or inverted.

The final auto-name run produced `Failed: 5, Passed: 0`:

- Scalar, invariant culture: `EnsureIndex(x => x.名称)` threw `ArgumentNullException` because its derived name was empty.
- Scalar, `tr-TR`: the distinct `$.Name` and `$.IName` expressions both derived `Name`, causing `IndexAlreadyExist`.
- Vector, invariant culture: `EnsureIndex(x => x.向量, options)` threw `ArgumentNullException` because its derived name was empty.
- Vector, `tr-TR`: the distinct `$.Embedding` and `$.IEmbedding` expressions both derived `Embedding`, causing `IndexAlreadyExist`.
- Culture transition: an index created for `$.IName` under invariant culture was created a second time under `tr-TR` instead of being recognized idempotently.

As a control, the same five cases passed when each auto-name call was temporarily replaced by an explicit expected name. That exercises every downstream catalog, query-plan, raw-document, and vector-search assertion and shows that the failures are confined to automatic name derivation.

## Double-entry coverage

- Both lambda and direct `BsonExpression` auto-name overloads are exercised for scalar and vector indexes.
- Exact name-to-expression pairs are read back as raw `$indexes` documents; names must be nonempty, unique, and exactly `Name`, `IName`, `名称`, `城市`, `Embedding`, `IEmbedding`, `向量`, and `向量二` as applicable.
- Two different non-ASCII fields prevent a constant fallback name from satisfying the test.
- Invariant and `tr-TR` runs require the same names, and a same-database culture transition must remain idempotent.
- Scalar query plans and results prove each generated index belongs to the intended field; vector query plans and nearest-neighbor results do the same for vector indexes.
- A raw BSON ledger independently verifies all scalar source values, preventing mapper-only compensation from making the typed queries look correct.
