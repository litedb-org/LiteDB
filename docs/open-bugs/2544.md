# Issue 2544: FileStorage upload performance after LiteDB 4

Source: https://github.com/litedb-org/LiteDB/issues/2544 (open on 2026-09-13).

## Result

The multi-fold slowdown reported for LiteDB 5.0.21 was **not reproduced on
dev**. A controlled Linux probe did find a smaller difference: dev's pooled
median for a 128 MiB upload was 563.732 ms, versus 414.180 ms for 4.1.4
(1.361x, or about 26.5% less throughput). The exact reported 5.0.21 package was
572.090 ms in an additional run. This is consistent with the maintainer's
separate observation that 5.0.21 was about 30% slower, but it is far below the
roughly 1.6x to 10.4x results in the reporter's tables. A maintainer also
measured dev and 4.1.4 at parity for a 512 MB upload on Windows/NVMe.

No executable regression was retained. The issue does not define an acceptable
ratio, representative storage setup, or repeatable end-to-end workload. Picking
a threshold between the observed 1.361x and one of the report's highly variable
ratios would invent a product contract. An absolute time would mostly test the
CI host. A green integrity-only ReproRunner entry would not test this bug and
could conceal a future performance regression.

## Complete report evidence

The GitHub body contains the synchronous `FileStorage.Upload(id, filename,
stream)` call but no standalone program or connection string. All five GitHub
comments and the attachment were inspected with `gh`. The attachment's five 1
GiB samples average 58 seconds on LiteDB 4 and 2:48 on LiteDB 5 (about 2.90x).
The later GitHub table reports different file sizes and empty versus 11 GB
caches; its ratios range from 1.63x for a 76 MB tree to 5.99x for a 135 MB
image.

The linked SDP-13037 YouTrack API became publicly readable during this audit.
It contains seven comments and seven original PNG attachments, including
evidence absent from the GitHub transcription:

- Windows DLL properties identify the tested package as
  `5.0.21+391cc9318c5be6e56cb71b3ce14b1ed9cb324763`.
- Another 1 GiB table reports 2:54 versus 0:58 for an empty cache and 5:34
  versus 0:32 for a 9 GB cache. The latter is 10.44x, illustrating strong
  cache-state or application-level variation.
- A second repeat reports 0.97x through 7.30x upload ratios. The 0.97x case has
  LiteDB 5 slightly faster for a 1 GiB file in a 6 GB cache, while the same
  table has LiteDB 5 about 7.2x slower for ten 20 MB files.
- File-open measurements are much closer: about 1.03x to 1.41x.
- Two attachments show successful copies larger than 2 GB/5 GB, and matching
  MD5 values. Thus the reporter supplied a useful integrity control, not a
  precise performance oracle.
- The cache limit was computed by the surrounding SDP application, and users
  also discussed leftover application temporary files and a varying cache cap.
  The external ticket was ultimately resolved as “Won't fix” after the
  application team chose not to use LiteDB 5.

Still missing are the exact LiteDB 4 patch, disk model/type, filesystem,
encryption or other connection-string options, whether source and database were
on the same disk, source-stream cache state, antivirus/filter-driver behavior,
the precise timed region, and a runnable workload. The “cache size” is also not
just a LiteDB parameter: the external comments say it is managed by SDP. These
variables can easily dominate buffered file I/O and database-growth timings.

## Source and existing-test audit

`LiteStorage.Upload` calls `OpenWrite` and `Stream.CopyTo`. The current writer
persists 255 KiB chunk documents with `_chunks.Insert` and upserts the file
metadata when the writer is flushed/disposed. The public FileStorage source in
this checkout is byte-for-byte unchanged from tag `v5.0.21`:

```sh
git diff --exit-code v5.0.21..HEAD -- LiteDB/Client/Storage
```

That source identity does not prove equal timings because engine and runtime
paths beneath the collection API can change. It does show that no documented
FileStorage-specific fast path or throughput contract was added on this dev
line. `LiteDB.Tests/Database/Storage_Tests.cs` exercises sub-megabyte upload,
replacement, metadata, and hash integrity. No FileStorage/upload benchmark is
present in `LiteDB.Benchmarks`. Neither the public API nor the issue states a
throughput or cross-version ratio.

## Controlled ReproRunner probe

The measurement used a temporary .NET 8 ReproRunner project and was removed
afterward because it is a benchmark without an agreed pass/fail oracle. It built
the same program against NuGet 4.1.4, the exact reported NuGet 5.0.21, and the
in-repository source. The ReproRunner invocation was:

```sh
dotnet run --project LiteDB.ReproRunner/LiteDB.ReproRunner.Cli -c Release -- \
  validate --id Issue_2544_FileStorageProbe
dotnet run --project LiteDB.ReproRunner/LiteDB.ReproRunner.Cli -c Release -- \
  run Issue_2544_FileStorageProbe --report /tmp/issue-2544-report.json
```

After ReproRunner's package-first execution, the same validated project was
built into separate directories and invoked in the opposite order. The exact
commands (with `probe_build=/tmp/litedb-2544-build-20260913`) were:

```sh
dotnet build LiteDB.ReproRunner/Repros/Issue_2544_FileStorageProbe/Issue_2544_FileStorageProbe.csproj \
  -c Release --nologo -p:UseProjectReference=false -p:LiteDBPackageVersion=4.1.4 \
  -p:OutputPath="$probe_build/v4/"
dotnet build LiteDB.ReproRunner/Repros/Issue_2544_FileStorageProbe/Issue_2544_FileStorageProbe.csproj \
  -c Release --nologo -p:UseProjectReference=true -p:LiteDBPackageVersion=4.1.4 \
  -p:OutputPath="$probe_build/dev/"
dotnet "$probe_build/dev/Issue_2544_FileStorageProbe.dll"
dotnet "$probe_build/v4/Issue_2544_FileStorageProbe.dll"
dotnet build LiteDB.ReproRunner/Repros/Issue_2544_FileStorageProbe/Issue_2544_FileStorageProbe.csproj \
  -c Release --nologo -p:UseProjectReference=false -p:LiteDBPackageVersion=5.0.21 \
  -p:OutputPath="$probe_build/v5/"
dotnet "$probe_build/v5/Issue_2544_FileStorageProbe.dll"
```

The probe used one untimed 8 MiB warm-up and seven measured 128 MiB uploads per
process. Every measured sample used a new database and the same deterministic
in-memory source, so input-disk contention, existing database size, data, and
file size were controlled. Payload generation, SHA-256, reopening, download,
verification, and deletion were outside the upload timer. After each upload it
also required all of the following:

1. `Upload` returned the exact length and consumed the complete source stream.
2. The database was disposed and reopened before verification.
3. `FindById` returned the exact length and filename.
4. `Download` returned every expected byte.
5. The downloaded SHA-256 matched
   `88A2B71649A6B87A6EA1726A77052A7FA154AF63EFE0418CBEC503DD317A3D72`.

Two 4.1.4/dev executions reversed process order to reduce systematic warm-cache
or machine-load bias. There were therefore 14 samples per variant:

| Order | 4.1.4 median | dev median | dev / 4.1.4 |
| --- | ---: | ---: | ---: |
| 4.1.4, then dev | 411.525 ms | 568.793 ms | 1.382x |
| dev, then 4.1.4 | 423.011 ms | 558.671 ms | 1.321x |
| pooled | 414.180 ms | 563.732 ms | 1.361x |

The pooled upload interquartile ranges were 409.495–465.387 ms for 4.1.4 and
530.344–631.979 ms for dev. Median throughput was 309.04 MiB/s and 227.06 MiB/s,
respectively. Timings through database disposal (including database open and
source `MemoryStream` construction) had pooled medians of 477.365 ms and
607.055 ms, a 1.272x ratio. Median database sizes were 136,921,088 bytes for
4.1.4 and 135,118,848 bytes for both 5.0.21 and dev. All persistence and content
controls passed.

The standalone 5.0.21 sample was:

```text
upload samples (ms): 641.820, 636.090, 582.908, 515.078, 528.774, 572.090, 518.753
median: 572.090 ms (223.74 MiB/s)
```

The raw upload samples for the order-reversed comparisons were:

This evidence supports keeping #2544 in “needs more information” rather than
claiming either performance parity or a current multi-fold dev regression. A
durable comparative benchmark becomes appropriate once the owner specifies the
representative connection string/storage topology, timed operation, cache
state, file-size distribution, and acceptable relative regression budget.
