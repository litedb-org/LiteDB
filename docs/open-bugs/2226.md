# Issue 2226: intermittent `EnterTransaction`/`EnterLock` invariant failure has no verified current-dev reproducer

Source: https://github.com/litedb-org/LiteDB/issues/2226 (open on 2026-09-13).

## Report evidence and contract boundary

The complete issue and timeline were read with:

```text
gh issue view 2226 -R litedb-org/LiteDB --comments --json number,title,state,labels,author,createdAt,updatedAt,body,comments,url
gh api --paginate -H 'Accept: application/vnd.github+json' repos/litedb-org/LiteDB/issues/2226/timeline
```

The issue has no comments, attached assets, database, or runnable reproduction. Its timeline contains only the original `question` label, a 2026-09-12 cross-reference from #2822, and the later severity/priority labels.

The report is for LiteDB 5.0.12, ASP.NET 6 on Windows Server 2019, a direct connection, and a scoped service which calls `BeginTrans()` at request start and `Commit()` at request end. After an unspecified amount of time, an insert fails at `Snapshot` construction with `LiteDB ENSURE: Use EnterTransaction() before EnterLock(name)` and later accesses remain unusable. It does not say whether a request awaits between those calls, whether every `BeginTrans`/`Commit` result is checked, which earlier exception occurred, which operations and collections run concurrently, or whether queries, rebuild, checkpoint, and disposal overlap.

That missing lifecycle detail is material. `ILiteDatabase.BeginTrans`, `LiteDatabase.BeginTrans`, and `LiteEngine.BeginTrans` explicitly document one transaction per thread. `TransactionMonitor` stores the current transaction in `ThreadLocal<TransactionService>`, while `LockService` uses a thread-affine `ReaderWriterLockSlim`. A write snapshot reaches the reported guard only after `GetTransaction`; in an ordinary same-thread `BeginTrans`/write/`Commit` lifecycle, `GetTransaction` first acquires the transaction read lock. Reaching the guard therefore requires an unreported thread hop or an earlier operation which desynchronizes transaction registration from lock ownership.

## Faithful same-thread request probe

A scratch .NET 8 console probe used one direct, file-backed `LiteDatabase` for 20,000 request-shaped operations under `Parallel.For` with maximum concurrency 8. Each synchronous callback called `BeginTrans`, inserted a document whose `_id` and independent `request` marker both identified the request, checked `Commit`, and never changed managed thread during the transaction. Failures attempted rollback on that same thread. Afterward, a fresh dedicated thread inserted a sentinel; the database was disposed and reopened; count, ID sum, and marker equality were checked independently.

Production source base: `094f2b8564d65ae37951e4d15104c624c53dafdd`. The three recorded repeats ran from working-tree commit `db092ed6d671736b4ca644179f0f9a5bc0154bab`, whose `LiteDB/` tree had no diff from that base. Environment: Ubuntu 24.04, Linux x64, .NET 8.0.30 runtime, .NET SDK 10.0.400.

Build/run command:

```text
dotnet run --project /tmp/litedb-2226-probe-Vz1Swb/Probe.csproj -c Release
for probe_run in 1 2 3; do dotnet run --project /tmp/litedb-2226-probe-Vz1Swb/Probe.csproj -c Release --no-build; done
```

All three recorded repeat runs produced the same invariants:

```text
requests=20000; workers=8; begin true=20000 false=0; commit true=20000 false=0; rollbacks=0; failures=0
live count=20000; id-sum=200010000; request-match=20000
follow-up joined=True; result=success:
reopened count=20001; id-sum=200030001; request-match=20001
```

Across 60,000 request transactions there was no exception, false transaction result, follow-up lock failure, missing/extra row, marker mismatch, or reopen failure. This is a bounded healthy probe, not evidence that the intermittent report is fixed.

## Forced-hop diagnostic (not an issue-specific regression)

A second bounded probe invoked eight async request scopes through their first incomplete await on one thread. Each scope called `BeginTrans` and inserted before the await. The caller then stayed blocked while continuations called `Commit` on pool threads. This deliberately violates the documented per-thread contract, but tests the likely ASP.NET failure mode suggested by #2822.

Observed on the same production tree:

```text
request 1: begin=True@T1; commit=False@T4; failure=none
request 2: begin=False@T1; commit=False@T6; failure=none
request 3: begin=False@T1; commit=False@T7; failure=none
request 4: begin=False@T1; commit=False@T8; failure=none
request 5: begin=False@T1; commit=False@T9; failure=none
request 6: begin=False@T1; commit=False@T10; failure=none
request 7: begin=False@T1; commit=False@T11; failure=none
request 8: begin=False@T1; commit=False@T12; failure=none
follow-up before cleanup: LiteException: Collection 'rows' lock timeout when entering in write mode after 00:00:01
owner rollback=True on T1
follow-up after cleanup: success:
reopened ids=2000
```

This does reproduce a silently orphaned transaction, an unusable subsequent writer, and loss of every request row after disposal. It does **not** reproduce the reported `EnterTransaction`/`EnterLock` exception. Because the issue never establishes a thread hop and the API documents thread affinity, this result is retained as a likely diagnosis rather than mislabeled as a #2226 regression. #2822 already owns the cross-thread explicit-transaction contract.

## Comparison with #1958

Result: 1 test, 1 failed at `Issue1958_Tests.cs:31`, “rebuild must not silently discard the active transaction”. #2226 never mentions rebuild, so importing that trigger would merely duplicate #1958 and would not verify this report.

## What is needed for a regression

An honest executable test still needs at least one of the following from the original environment: a minimal application or database, managed-thread IDs at `BeginTrans`/write/`Commit`, the first exception before the repeated invariant failures, or confirmation of async/query/rebuild/checkpoint/disposal overlap. It should also capture every boolean transaction result and the request's rollback/finally behavior. Windows-specific behavior remains untested by the Linux probe.

No #2226 test or ReproRunner case is added: the faithful reported lifecycle is healthy on current dev, while the only deterministic failure requires an unstated, documented-misuse thread hop and produces a different exception.
