# Issue 2871: constructor cache permits concurrent `Dictionary` reads and writes

Source: https://github.com/litedb-org/LiteDB/issues/2871 (open on 2026-09-13;
the issue has no comments).

## Contract and independent checks

`Cache_hits_remain_correct_while_unique_constructor_types_force_resizes` uses
the real internal `Reflection.CreateInstance` entry point. It warms one reader
type, then releases four dedicated cache-hit readers alongside one writer. The
writer constructs 4,096 issue-private closed generic types that cannot have
been cached by another test. When the implementation is the current plain
`Dictionary<Type, CreateObject>`, the fixture reads its live bucket capacity
and count and requires the 4,096 additions to cross a capacity boundary. This
proves the run includes a resize instead of merely assuming that it does.

Every reader performs at least 4,096 hits and continues until the writer is
done. The workload has a 30-second completion deadline and a 45-second xUnit
timeout. Worker exceptions are collected rather than lost in background tasks.
After the concurrent phase, all 4,096 types are constructed again. Each result
must have the exact requested runtime type, preserve both generic arguments
and the constructor-set value, and be a fresh object rather than the first
instance. The warmed reader receives the same type/value/fresh-identity checks
both during and after the stress phase. An `IList<T>` construction also checks
that the cache change does not break the interface-to-concrete recursion path.

The second test is a deterministic concurrency invariant for the reported
legacy implementation. It owns the existing constructor dictionary's monitor
and first releases a dedicated cache-miss writer for an issue-private type. It
requires that real production writer to wait for this monitor, then releases a
warmed cache-hit reader and requires the reader to wait too. Current code blocks
the writer but lets the unlocked hit complete, so the test fails deterministically.
Requiring both sides closes a false-green loophole where a change could move only
writes to an unrelated lock while leaving reads unsafe. If the cache is replaced
by a non-`Dictionary` implementation, the dictionary-monitor-specific assertion
is not applied. Thus the test permits `ConcurrentDictionary` or immutable/
copy-on-write storage; a retained mutable `Dictionary` must use one verifiable
monitor for all access.

The stress and the independent coordination check close complementary gaps: a
stochastic run alone can pass without landing in a resize's vulnerable window,
while the monitor check alone could be made green without preserving actual
constructor behavior.

This remains a unit test rather than a ReproRunner program because the defect
is an in-process private static cache and the test assembly already has the
required internal access. A process/OS matrix adds no missing boundary here;
the three project target frameworks are exercised below.

## Source evidence on dev

Audited and executed base: `f197a147dd7ff2319f4bee7015ccc7066b95a17b`.

At that SHA, `LiteDB/Client/Mapper/Reflection/Reflection.cs` declares
`_cacheCtor` as a plain static `Dictionary<Type, CreateObject>` on line 30. The
first `TryGetValue` runs before any lock on line 39. Only the second lookup and
the class/struct additions on lines 53, 62, and 94 are inside
`lock (_cacheCtor)` beginning on line 49. Thus a cache-hit reader can execute
against the same dictionary while another thread mutates or resizes it.

## Observed execution

Release, Linux, .NET 8:

```sh
dotnet test LiteDB.Tests/LiteDB.Tests.csproj -c Release -f net8.0 \
  -p:TestingEnabled=true --no-restore --settings tests.runsettings \
  --filter FullyQualifiedName~Issue2871_ --logger 'console;verbosity=minimal'
```

Result: **1 passed, 1 failed**. The bounded 4,096-type concurrent stress passed;
no exception, hang, missed/corrupt value, wrong type, or reused identity was
observed in that run. The deterministic test failed because the warmed cache
hit completed while a real cache-miss writer was waiting on the constructor
dictionary's monitor. The two-test execution took about one second.

Both legacy targets compile the same source with zero errors:

```sh
dotnet build LiteDB.Tests/LiteDB.Tests.csproj -c Release -f net461 \
  -p:TestingEnabled=true --no-restore --nologo --verbosity:minimal
dotnet build LiteDB.Tests/LiteDB.Tests.csproj -c Release -f net481 \
  -p:TestingEnabled=true --no-restore --nologo --verbosity:minimal
```

The host has no native Mono executable, so the already-present Mono container
and matching xUnit console runners executed the built assemblies:

Each legacy run also produced **1 passed, 1 failed**. The stress test passed and
the same deterministic monitor invariant failed; total execution was 1.649 s
for `net461` and 1.680 s for `net481`.

These results confirm the unsafe source structure and deterministically expose
the unprotected cache hit, but they do **not** claim that a runtime exception,
wrong result, or infinite loop was reproduced. The nondeterministic stress run
was clean on all three runtimes. The bug still applies because the production
code permits the forbidden reader/writer overlap; the paired tests distinguish
that evidence from an observed corruption event.
