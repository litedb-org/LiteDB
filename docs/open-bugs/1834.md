# Issue 1834: `TryEnterReadLockCore` while executing a Xamarin Forms query

Source: https://github.com/litedb-org/LiteDB/issues/1834 (open on 2026-09-13).

## Report fidelity and platform limit

The complete issue and both comments were read with `gh`. The report contains only
an iOS/Mono stack trace ending in `Enumerable.Any`; it does not identify the
exception type, LiteDB version, connection mode, preceding database operations,
or a reproducer. A maintainer explicitly requested those missing details. This
Linux/.NET 8 environment cannot execute Xamarin/iOS code, so the reporter's exact
failure cannot be confirmed honestly.

The regression test therefore exercises the strongest bounded candidate for the
reported stack: a public deferred query is first advanced on one dedicated
thread, disposed after a thread handoff, and then followed on the original thread
by the same `LiteQueryable -> MoveNext -> Enumerable.Any` path shown in the
report. This is a real user-visible lock failure with the same stack shape, but it
is not proof that the Xamarin report had the same trigger. No iOS-specific claim
should be made until the reporter supplies the missing exception and lifecycle
details.

## Independent checks

- A same-thread healthy-control query must agree with CLR LINQ over the input
  array before the handoff is attempted.
- The post-handoff LiteDB `Any` result must still agree with that independent CLR
  oracle; merely suppressing the lock exception cannot satisfy this assertion.
- A separate exclusive `Checkpoint()` must complete, independently detecting a
  stranded transaction read lock.
- A final full scan must retain the three original IDs, preventing lock handling
  changes from hiding the symptom by losing or changing data.
- Every coordination wait and thread join has a finite timeout, and the worker is
  a background thread, so a regression is reported as a failure rather than
  hanging the test process.

## Observed on the PR worktree

PR: https://github.com/litedb-org/LiteDB/pull/2877, whose `dev` base was
`094f2b8564d65ae37951e4d15104c624c53dafdd` when inspected. The focused run was
started from WIP parent `c123a8bf83e413b1a0e8c7ed3ea4df30a6d88316` plus the
uncommitted issue test (Release, .NET 8, Linux). The shared branch advanced during
the run only by unrelated issue test/document commits; no `LiteDB/` production
source changed between that parent and `89820a3b0a8575e6d126d0b7ff6a9b920dc2078b`.

Result: **failed as a candidate reproduction** in 1 second.

- The healthy control passed.
- The original query thread's subsequent `Any()` threw
  `System.Threading.LockRecursionException: Recursive read lock acquisitions not
  allowed in this mode`, beginning at
  `ReaderWriterLockSlim.TryEnterReadLockCore` and continuing through
  `LockService.EnterTransaction`, `TransactionMonitor.GetTransaction`,
  `QueryExecutor.ExecuteQuery`, `LiteQueryable.ToDocuments`, and
  `Enumerable.Any`, matching the reported stack shape.
- Because the query never returned, the independent expected-`true` oracle saw
  no result.
- The independent checkpoint then threw `LiteException: Database lock timeout
  when entering in exclusive mode after 00:00:01`, confirming that a transaction
  read lock remained stranded.
- The final ID scan still returned the original rows.

Executed command:

```text
dotnet test LiteDB.Tests/LiteDB.Tests.csproj -c Release -f net8.0 --no-restore -p:TestingEnabled=true --settings tests.runsettings --filter FullyQualifiedName~Issue1834_Tests
```

This evidence warrants keeping a regression test, while the issue should remain
labelled as needing more information for Xamarin-specific diagnosis.

## Manual sweep resolution (2026-09-17)

The retained cross-thread disposal case is fixed by the counted transaction gate
in 90a5f363 (#2790). Cleanup removes the exact transaction once and releases its
read lease using the recorded creator thread ID, so foreign disposal cannot
strand that owner's lock. The subsequent owner query and exclusive checkpoint
remain independently validated. The unchanged regression passes in the current
full suite (`p2-1162-w4-integrated.trx`). Four fresh independent Sol-high closure
reviews found no defects in this bounded path. The missing original Xamarin/iOS
exception and lifecycle details remain necessary for a platform-specific claim.
