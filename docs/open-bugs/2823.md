# Issue 2823: v4 upgrade aborts on duplicate `_id` values

Source: https://github.com/litedb-org/LiteDB/issues/2823 (open on 2026-09-13).
The public real-world fixture comes from the linked report
https://github.com/litedb-org/LiteDB/issues/2405.

## Contract and independent ledgers

An upgrade cannot recreate two v5 `_id` index entries that compare equal under
the requested target collation. It must retain one source document for each
distinct target key and write one durable `_rebuild_errors` row for every source
occurrence it skips. The two counts must add back to the source count.

`Issue2823_Tests` embeds two compressed v4 files and verifies their SHA-256 before
opening either one with current LiteDB:

- The 32 KiB `Data.db` attached to #2405 has SHA-256
  `65891347e8e8c87ff2ff4ab90f47c2b87884dd22d2c80cfe36affafe171752f4`.
  Reading that source with the independently restored LiteDB 4.1.4 package
  produced 31 `ItemInfo` rows, 26 ordinal-distinct IDs, and five duplicated IDs:
  `.LastTestplan`, `.MeasPointChartDisplayLinear`,
  `.MeasPointChartSettings`, `.MeasPointChartShowRawProfile`, and
  `.MeasPointChartShowSelection`.
- A purpose-built LiteDB 4.1.4 file has SHA-256
  `140394df0a41b5903542380e73cffb574861256c315abe37a9883183f8e34921`.
  It contains two healthy controls plus `Case Twin.LastGageMode` and
  `case twin.lastgagemode`, with different payloads. They are ordinal-distinct
  source IDs, while the .NET `en-US` ignore-case comparer independently confirms
  that they are one target key.

The real fixture's complete ID-set hash and all 21 nonduplicate ID/payload pairs
are fixed in the test. Each of the five surviving duplicate values must also hash
to an actual source value (either original chart-settings value is accepted).
This prevents implementations that merely catch the exception while dropping
unrelated rows, inventing replacement data, or omitting an error entry. Each
error row must identify both its collection and duplicate ID; the case-collision
case must identify the exact source spelling that was skipped.

Both cases reopen the result with `Upgrade=true`, compare the full data/error
snapshot, verify that the byte-identical v4 backup was not replaced, and require
the directory to contain only `data.db` and `data-backup.db`. The async xUnit
timeout is 30 seconds.

## Expected correct result

Both tests pass. The real file publishes 26 documents plus five error rows. The
case fixture publishes three documents plus one error row. Healthy controls and
all nonduplicate payloads survive, the ledgers balance their respective source
counts, retry is a no-op, and no `data-temp*` file remains.

## Observed on dev

Dev baseline tested: `dd016a4baf2f636e342bdf25adce3dda5fc39de7`,
with `Issue2823_Tests.cs` added and no production changes; Release, .NET 8,
Linux.

The final test source was built and then run from a disposable one-file xUnit
project so concurrently edited, unrelated test files could not affect the
result. Exact focused command executed:

```bash
dotnet test /tmp/issue2823-isolated-tests/Issue2823.Isolated.Tests.csproj -f net8.0 -c Release -p:TestingEnabled=true --no-build --filter 'FullyQualifiedName~Issue2823' --artifacts-path /tmp/issue2823-final-isolated-alltfm-artifacts
```

Two tests were discovered and both failed, as the correct-behavior assertions
require while the bug remains:

- The real fixture aborts in `LiteEngine.RebuildContent` with
  `Cannot insert duplicate key in unique index '_id'. The duplicate value is '".LastTestplan"'.`
- The case fixture aborts in the same path with
  `Cannot insert duplicate key in unique index '_id'. The duplicate value is '"case twin.lastgagemode"'.`

The standard repository test-project command was also executed successfully
through discovery at `26ccb535c3bfe83c4e32195f4ddf76174c9a0889` (only
other tests and docs differ from the SHA above) and produced the same failures:

```bash
dotnet test LiteDB.Tests/LiteDB.Tests.csproj -f net8.0 -c Release -p:TestingEnabled=true --filter 'FullyQualifiedName~Issue2823' --artifacts-path /tmp/issue2823-final-standard-artifacts
```

The test source was compiled against the repository project reference for every
`LiteDB.Tests` target with this exact command:

```bash
dotnet build /tmp/issue2823-isolated-tests/Issue2823.Isolated.Tests.csproj -c Release -p:TestingEnabled=true --artifacts-path /tmp/issue2823-final-isolated-alltfm-artifacts
```

That build succeeded for `net461`, `net481`, and `net8.0` with zero errors. A

As a satisfiability check, a disposable copy at

Those production edits exist only in the disposable copy and are not part of
this regression-test change.

## Limitations

The test requires cleanup after a successful tolerant upgrade and after its
subsequent retry. It does not inject an unrelated I/O or corruption failure, so
it does not prove cleanup of temp files after every possible fatal upgrade path.
It deliberately does not prescribe whether the first or last exact duplicate
survives, provided the survivor is an actual source document and the skipped
occurrence is reported. Current status: **reproduced**.
