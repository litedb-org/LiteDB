# Issue 2163: mixed Direct and Shared access can silently lose writes

Source: https://github.com/litedb-org/LiteDB/issues/2163 (open on
2026-09-14).

## Observed on dev

The bounded two-process ReproRunner case
`Issue_2163_MixedAccess` reproduces on both package 5.0.21 and current `dev`.
Each variant exits `0` with `BUG_2163_CONFIRMED`.

The Direct owner begins a transaction and reads a one-row snapshot. Before that
owner releases the file, a Shared process successfully inserts row 202,
checkpoints, reopens, and verifies it. The Direct owner still sees only its
stale baseline, then successfully inserts row 303, commits, and checkpoints.
Two independent final reopens contain exactly rows 101, 303, and the later
non-overlapping Shared control 404. A fsynced external receipt exists for row
202, but row 202 alone is absent from both the primary collection and its
unique token index.

## Double-entry checks

- Two actual processes use the same database path under the runner's isolated
  shared directory; no in-process engine sharing substitutes for the collision.
- Every acknowledged operation has an external JSON receipt containing exact
  IDs, writer/process identity, a 2 KiB patterned payload, and a SHA-256 digest.
- The contender verifies its write through a fresh Shared instance before the
  Direct owner proceeds.
- The final oracle compares all document fields, primary IDs, the unique token
  index, unexpected and malformed rows, then checkpoints and reopens again.
- A Shared insert/checkpoint/reopen after Direct disposal must succeed, so
  blanket rejection or a permanently poisoned file is not classified as fixed.
- Fail-fast ownership rejection, true serialization, stale-owner rejection,
  and full durable preservation are accepted repairs. Any unrelated crash,
  exception, timeout, or different corruption exits `20` as a harness failure.

Run:

```sh
dotnet run --project LiteDB.ReproRunner/LiteDB.ReproRunner.Cli -- \
  run Issue_2163_MixedAccess
```
