# Issue 1848: independent read-only connection bypasses writer ownership

## Reproduced ownership failure on current dev

`Issue1848_ReadOnlyOwnershipTests` covers the independent Direct read-only
connection in the current issue title. The old in-memory test below used one
shared instance and could not exercise that boundary.

The new test checks a real file and a unique secondary index. The same read-only
configuration reads every row before the writer opens and after it closes. While
the writer owns the file and has an acknowledged WAL-only insert, the independent
reader must refuse access with an ownership-specific error. Both the writer and
a fresh reopen must retain all acknowledged IDs, tokens, and payloads; subsequent
writer inserts must still work. Thus rejecting every reader, closing the actual
writer, losing its WAL, or reporting an unrelated exception cannot pass.

On `dev` at `a50661a9`, all data controls pass but the reader is admitted, so
the ownership assertion fails. This reproduces the unsupported admission
boundary; it does not claim to recreate the original large-database OOM or the
specific `Invalid Collection` page from the report.

Validation: Linux/.NET 8, **one repro failed and one shared-instance control
passed** with `--filter FullyQualifiedName~Issue1848`.

Source: https://github.com/litedb-org/LiteDB/issues/1848 (open on 2026-09-12).
