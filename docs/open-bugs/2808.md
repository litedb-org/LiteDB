# Issue 2808: publish a patched LiteDB v4 security release

Source: https://github.com/litedb-org/LiteDB/issues/2808 (open on
2026-09-13).

## Regression-test boundary

**No executable test is retained in this `dev`-branch test project.** The issue
does not report a defect in the assembly built from `dev`; it requests a tag and
NuGet publication from the separately maintained `v4` branch. A passing test of
the current `DefaultTypeNameBinder` would be false evidence: `dev` already has
the broader block list, while every published v4 package could remain
vulnerable. Conversely, a test which queries GitHub or NuGet during normal CI
would be a network-dependent release monitor rather than a deterministic source
regression.

A ReproRunner pinned to 4.1.4 would only reconfirm the known vulnerable
artifact. It could not turn green when a future 4.1.5 is published without
changing its package reference, and testing the untagged `v4` source would not
prove that those bytes reached NuGet. Either approach would let code coverage
stand in for the missing deliverable that the issue actually asks for.

## Repository and release evidence

The issue, related pull requests, tags, releases, advisory, and live `v4`
branch were inspected with `gh` on 2026-09-13:

- GitHub's advisory still rates GHSA-3x49-g6rc-c284 / CVE-2022-23535 as
  critical. Its sole NuGet range is `< 5.0.13`, and its first patched version is
  5.0.13. It therefore still classifies every 4.x package as vulnerable.
- The newest v4 tag, GitHub release, and NuGet version are all 4.1.4. Tag
  `v4.1.4` resolves to `918b6500b16bcb85a1d2e713c5486bd6491f9016`; the
  release was published on 2018-06-20. NuGet's flat-container index contains
  no 4.1.5.
- The live `v4` branch resolves to
  `3af2be2b91b365ea04b2f5e5255d2ba91ebb14c6`, the 2024-06-19 merge of PR
  #2424. It is 62 commits ahead of `v4.1.4`, and its project declares version
  4.1.5, but neither a version declaration nor an untagged branch is a released
  package.
- PR #2465 is no longer open, despite the issue body's earlier snapshot. It was
  closed without merge on 2026-09-13 as superseded by #2424.

The merged backport is also narrower than the current implementation. Its
deserializer first rejects a resolved `_type` which is not assignable to the
declared member, then hard-codes one forbidden type:
`System.Diagnostics.Process`. Its added `Class_Not_Assignable` test covers only
the first rule. Current `dev` resolves through `ITypeNameBinder` and its default
binder rejects 35 known type names, including `ProcessStartInfo`,
`ObjectDataProvider`, `XamlReader`, `WindowsIdentity`, `ResXResourceReader`,
PowerShell, NLog, and other gadget families. The author of #2424 independently
warned in #2556 that the v4 patch was probably insufficient for this reason.

This means publishing the current `v4` head as-is would satisfy the missing
version number but would not establish parity with the security boundary used
by supported versions.

## Required source verification before release

A v4.1.5 candidate needs tests in the `v4` branch, against the v4 mapper, rather
than tests compiled against `dev`. At minimum they must establish both sides of
the boundary:

1. Reject an unassignable `_type` before constructing it.
2. For members declared as `object`, dictionary values, and enumerable items,
   reject representative types from every gadget family blocked by the current
   default binder. `System.Diagnostics.Process` alone is not sufficient.
3. Use a custom type-instantiator counter and require it to remain zero, so a
   catch-after-construction implementation cannot make the tests green.
4. Preserve benign polymorphic deserialization for a known, assignable
   application type. Blanket rejection of every `_type` is not a valid fix.
5. Assert the stable security-specific `LiteException` code and rejected full
   type name, not merely that some exception occurred.
6. Build and execute the checks for every framework the v4 package promises:
   `netstandard1.3`, `netstandard2.0`, and, on Windows, `net35` and `net40`.

The candidate should either port the same maintained binder policy as `dev` or
document and test an equally strong allow-list design. Copying a hand-picked
subset without a parity check would allow the two branches to drift again.

## Required artifact verification before closing

The issue is resolved only when the independently downloaded package—not a
local project reference—passes all release checks:

1. An annotated `v4.1.5` tag exists and peels to the reviewed candidate commit;
   that commit contains the complete security tests and is a descendant of the
   intended v4 history.
2. A non-draft GitHub release exists for exactly that tag, and NuGet's
   registration/flat-container endpoints expose stable package `LiteDB`
   version 4.1.5.
3. Record the SHA-256 of the downloaded `.nupkg`. Inspect its nuspec and each
   DLL to require package, assembly, and file version 4.1.5 and only the promised
   target-framework assets.
4. Restore a clean consumer with only `LiteDB` 4.1.5 from nuget.org, with no
   source/project fallback, then run the same hostile and benign mapper cases
   used for the candidate. The instantiator counter and exact diagnostics must
   match.
5. Run the same artifact harness against 4.1.4 as a negative control and require
   it to exhibit the pre-fix vulnerability. This prevents a harness that never
   reaches LiteDB deserialization from blessing both packages.
6. Update the GitHub advisory so its version ranges distinguish the repaired
   v4 line from the repaired v5 line. Verify the four boundaries explicitly:
   4.1.4 vulnerable, 4.1.5 patched, 5.0.12 vulnerable, and 5.0.13 patched.
7. Repeat the NuGet restore after cache eviction and propagation. Only then can
   the release request be closed; a tag, branch version, or locally packed file
   by itself is insufficient.

Useful live-state checks are:

```sh
gh issue view 2808 -R litedb-org/LiteDB \
  --json number,title,state,labels,body,comments,updatedAt,url
gh pr view 2424 -R litedb-org/LiteDB \
  --json state,mergedAt,mergeCommit,baseRefName,files,url
gh pr view 2465 -R litedb-org/LiteDB \
  --json state,closedAt,mergedAt,mergeCommit,baseRefName,url
gh api repos/litedb-org/LiteDB/branches/v4
gh api repos/litedb-org/LiteDB/compare/v4.1.4...v4
gh api repos/litedb-org/LiteDB/tags --paginate \
  --jq '.[] | select(.name | startswith("v4")) | [.name,.commit.sha]'
gh release list -R litedb-org/LiteDB --limit 100
gh api /advisories/GHSA-3x49-g6rc-c284
curl -fsSL https://api.nuget.org/v3-flatcontainer/litedb/index.json
```

After publication, the first two commands should be supplemented with
`gh release view v4.1.5 -R litedb-org/LiteDB --json tagName,isDraft,isPrerelease,assets`.

## Executable publication audit (2026-09-15)

The standalone `python3 scripts/regressions/issue_2808.py` now makes the release
boundary above reviewable without executing deserialization. It queries NuGet,
downloads and checks package identity/assemblies/hashes, compares tag ancestry
with the merged backport, and checks advisory affected/unaffected controls.
It observed stable v4 **4.1.4**, whose tag lacks the backport and which the advisory
still classifies as affected. It exits 1 with `BUG_2808_PUBLICATION_CONFIRMED`.

This is publication/metadata evidence, not a runtime security verdict. A network,
identity, range-parser, or control failure exits 2; a future matching publication
and advisory exits 0. Source tests alone still cannot establish release completion.
