# Issue 1224: Implicit BsonValue from ulong operator casts to double instead of long.

Source: https://github.com/litedb-org/LiteDB/issues/1224 (open on 2026-09-12).

## Contract and independent checks

The implicit conversion is checked against independently authored signed `Int64`
values and exact BSON type/payload bytes, including the first value above
`Int64.MaxValue`, a nontrivial high-bit pattern, and `UInt64.MaxValue`. A typed,
indexed collection is written in reverse order, reopened, inspected through the
raw API, queried through the `ulong` mapper path, and read in both index orders.
This prevents matching encoder/decoder errors, a primary-key-only workaround, or
a `double` representation that happens to preserve a few small values from
making the regression green.

## Observed on dev

Base: `90788bace880f477c9fb52ff7c0da98c9700bdfe`; Release, .NET 8, Linux.
`11/11` tests fail: five inputs are still encoded as `Double`, five
independently authored `Int64` values throw while converting back to `UInt64`,
and the persisted upper-half key cannot be found through `FindById(ulong)`.
The raw reopened documents, both primary-index order controls, and indexed typed
value queries for all four upper-half values complete before that ID lookup
fails. Assertions describe correct behavior; failures are not marked skipped or
inverted.

Run: `dotnet test LiteDB.Tests -c Release -f net8.0 -p:TestingEnabled=true --settings tests.runsettings --filter FullyQualifiedName~Issue1224_`.
