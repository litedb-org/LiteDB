# Issue 2738: Android encrypted-database creation reports "File is not encrypted"

Source: https://github.com/litedb-org/LiteDB/issues/2738 (open on
2026-09-13).

## Status

**The Android/new-file claim is not reproduced.** A native creation control and an actual Android APK driver are
retained in `LiteDB.Tests/Issues/Issue2738_NativeControlTests.cs`; its passing
result must not be treated as an Android regression or evidence of a fix.
The issue does establish a real exception, but not the file state or
operation that produced it. A bounded Linux probe stayed healthy on the exact
5.0.21 NuGet package and current `origin/dev` in Direct and Shared modes, under
.NET 8 and .NET 10. It covered ordinary creation, supported concurrent creation,
process termination, and interruption at every write which constructs the
encrypted prefix.

The exact exception is reproducible when a file at least one page long already
exists and its first byte is not the encrypted marker `1`. That is a sensitivity
control, not evidence that LiteDB created such a file on Android.

## Retained native control (2026-09-14)

The four cases cover Direct/Shared access with an absent path or an existing
zero-length file. They execute a real insert (the Shared constructor alone is
lazy), create a unique secondary index, checkpoint, dispose, and reopen. A
second generation updates one row and deletes another; two further reopens
must match an external ledger through a full scan, primary-key lookup, and the
secondary index. The ledger checks exact keys, generation, unique tokens, and
all 257 nonuniform payload bytes. The file prefix must still indicate encryption
after each writing instance closes, and the user version must survive.

The test is marked `IssueStatus=UnconfirmedPlatform` so discovery and the
coverage inventory can distinguish it from a verified Android reproduction.
It makes the earlier healthy lifecycle investigation repeatable while retaining
the missing-platform boundary. The original Android report still needs the
project/file-state information listed below.

## Boundary with #2824

#2824 is the confirmed rebuild defect. On an encrypted database, parameterless
`Rebuild()` creates and swaps in a plaintext replacement and then fails while
reopening it with the old encrypted settings. That leaves exactly the kind of
pre-existing plaintext file which later raises #2738's stack. It is one possible
provenance, but #2738 never says that `Rebuild()` or SQL `REBUILD` ran.

This checkout already covers that operation under its own issue number:

- `LiteDB.Tests/Issues/Issue2824_Tests.cs` asserts that parameterless rebuild
  must preserve encryption and that password-changing rebuild must leave the
  instance and file usable;
- both correct-behavior cases are recorded failing in
  `docs/open-bugs/2824.md`; and
- the coverage was introduced by
  `a98a72da6047c47056be9fc5ea8477e1fed07f21`.

Adding the same rebuild sequence as an `Issue2738` test would duplicate #2824
and would falsely claim that the reporter's Android creation history was known.

## What the exception proves

The relevant creation decision is the same in the published 5.0.21 source
identified by its package metadata
(`391cc9318c5be6e56cb71b3ce14b1ed9cb324763`) and tested dev
`a50661a9d1a25b5713586d0096c6325d76bf5dfe`:

1. `AesStream` treats an underlying stream shorter than 8,192 bytes as new.
2. For a new stream it writes byte `1`, a 16-byte salt, an encrypted 32-byte
   password check, and extends the hidden encryption page to 8,192 bytes.
3. Only when the stream is already at least 8,192 bytes does it read byte zero
   and throw `FileNotEncrypted` if that byte is not `1`.
4. `DiskService` then writes the database header as the second physical page.

The two source revisions differ in later lifecycle cleanup, but not in this
classification or write order. The relevant dev blob IDs were:

```text
AesStream.cs          c256f2ee29a64706bc80854c1d0709080bb849b9
FileStreamFactory.cs  9c344daab76da9c3942e06bc00e706eb0021039d
DiskService.cs        28db484577135b79a15540d8ff2c5651ccf264c0
SharedEngine.cs       1b7bb0b0cd665d67bcb4b50c46487795fe407108
```

Consequently, this stack proves that `AesStream` first observed a length of at
least one page and then read a first-byte value other than `1`. Without a
concurrent mutation, that means a full non-encrypted page was already present.
It does not identify who created or replaced that stream. A genuinely absent
ordinary local file begins at length zero and follows the new-stream branch.

## Bounded probe

A temporary strict console harness was built against four combinations:

- NuGet `LiteDB` 5.0.21 under .NET 8.0.30 and .NET 10.0.11. The downloaded
  package SHA-256 was
  `938a4f5f9d6a28383de8ccfcbdb8897e78432399215232cf38dbf147e03ec167`;
  its selected `netstandard2.0/LiteDB.dll` SHA-256 was
  `ae31ac6a93549217b9e8b81497d1ee831658ade6df9e1ee20f2838f22de5e218`.
- Source build at exact detached `origin/dev`
  `a50661a9d1a25b5713586d0096c6325d76bf5dfe`, under the same two runtimes.
  The net8 and net10 LiteDB DLL SHA-256 values were respectively
  `3f1a2197e529b7328cae8ea8c5402f906ea6e0a385c562c4468f2da58126ef64`
  and
  `54fedb4e9888facc44acbfa520db4977b6a440ffcd1da08733e6d2a139190271`.

Host: Ubuntu 24.04.3, Linux x64, filesystem type reported as `ext2/ext3`, .NET
SDK 10.0.400. Each of the four build/runtime combinations ran the same matrix:

| Case | Direct | Shared | Required oracle | Result |
| --- | ---: | ---: | --- | --- |
| Fresh sequential path | 128 | 128 | marker `1`, page alignment, exact row after correct-password reopen, passwordless open denied | passed |
| Concurrent first use, 32 rounds x 8 | eight distinct absent paths per round | eight instances sharing one absent path per round | exact ID/marker ledger after reopen | passed |
| True multi-process first use | not applicable to Direct's unshared ownership | 12 rounds x 8 processes on one absent path | all eight IDs in every round (96 child writes total) | passed |
| Kill after path appeared, then recover | 96 | 96 | encrypted recovery write, checkpoint, passwordless denial, exact sentinel after reopen | passed |
| Pre-created short-file controls | lengths 0, 1, 17, and 8,191 | same | converted to a valid encrypted database | passed |
| Pre-created 8,192-byte zero-file sensitivity control | 1 | 1 | exact `File is not encrypted` exception | passed |

Each harness run therefore completed 256 ordinary fresh creations, 64
concurrency rounds, 12 true multi-process Shared rounds, 192 killed-process
recoveries, eight short-file controls, and two exact-exception controls with no
failure. Direct concurrency used independent files; multiple owners of one file
are the Shared-mode scenario and the reported stack is itself Shared.

The ordinary kill loop terminated a child immediately after the database path
appeared, with 1 ms and 5 ms delayed variants mixed in. Before recovery, every
observed data file was 16,384 or 40,960 bytes and began with `1`. That sampling
could miss the very short prefix-writing window, so a second probe interrupted
specific syscalls rather than relying on timing.

## Exact write-interruption probe

On Linux, `strace` showed creation of the encrypted prefix as the first four
`pwrite64` calls: marker plus salt, password check, extension of the hidden page,
then the database header. Signal injection delivered `SIGKILL` before writes one
through five. The pre-recovery states were identical in Direct and Shared mode,
on both builds and both runtimes:

| Interrupted write | File length | First byte |
| ---: | ---: | ---: |
| 1 | 0 | absent |
| 2 | 17 | 1 |
| 3 | 64 | 1 |
| 4 | 8,192 | 1 |
| 5 | 16,384 | 1 |

All 40 combinations (five write points x two modes x two builds x two
runtimes) were then reopened with the password, given a unique recovery row,
checkpointed, rejected without a password, and reopened again with the exact
recovery row intact. Every recovery process returned zero. This directly checks
the partial states that the timing-based kill loop did not observe, but only for
Linux file-system semantics.

The temporary harness and its outputs were removed because all supported cases
were healthy. Retaining a green Linux test under #2738 would test generic
encrypted-file creation, not the missing Android trigger, and could misleadingly
imply that the report was fixed or disproved.

## Platform limit and required artifact

The initial native investigation had no Android runtime. The later emulator
comparison below covers app-private Android storage, but still cannot decide
whether an Android-specific storage provider, application bootstrap race,
backup/asset restore, path alias, or named-mutex behavior causes another actor
to place a full plaintext page at `dbPath`. The issue also does not say whether
the path is app-private storage, external/scoped storage, or an abstraction over
a nonordinary file.

The highest-value required artifact is the failing Android `.db` together with
its matching `-log.db`, captured immediately after the first exception and
before retry, rebuild, copy, or deletion. Include a directory listing with the
sizes and timestamps of `-backup.db`, `-temp.db`, and other same-basename files.
That bundle distinguishes an empty/partial encrypted creation from a valid
plaintext database, a preallocated zero page, a replaced file, or recovery
residue.

To establish the stronger claim that the path was genuinely absent, a runnable
minimal Android project or equivalent before/after trace is also required. It
must record, immediately before the first engine-triggering operation and again
in its catch block:

- the canonical absolute path, `File.Exists`, length, and first byte;
- the complete `ConnectionString`, especially `Connection=Shared`;
- target framework, Android API/device, storage directory/provider, LiteDB
  assembly informational version and hash;
- the exact first operation after constructing `LiteDatabase`;
- every concurrent task/process which can touch the path; and
- whether startup code calls `File.Create`, `SetLength`, copies an asset or
  backup, opens without a password, or calls `Rebuild`/SQL `REBUILD`.

With that artifact, a regression can preserve the failing file as a fixture or
reproduce the Android operation which creates it. Until then #2738 remains
unconfirmed and distinct from the executable #2824 rebuild regression.

## Actual Android follow-up (2026-09-15)

The .NET 10 Android workload and an Android 15/API 35 Google APIs x86_64 emulator
were installed for the historical comparison. The retained APK ran 12 cases
against **5.0.21** and 12 against **dev `a50661a9`**, then a second driver invocation
repeated all 24 successfully. Direct/Shared mode and absent/pre-created-empty paths
all preserved encrypted headers, acknowledged payloads, updates, deletion, and
secondary-index results across independent reopens. Both builds ran on Android
with .NET 10.0.11; build success alone is not counted.

[APK driver and commands](../../tools/Issue2738Android/README.md),
[captured Android reports](evidence/2738-20260915.json).
The claim remains unconfirmed for the reporter's unknown file/storage lifecycle;
the missing Android runtime is no longer the reason. No rebuild scenario is
substituted for the reported fresh-file creation.
