# Issue 2195: index free-list head reports slot 1 during `Insert`

Source: https://github.com/litedb-org/LiteDB/issues/2195 (open on 2026-09-13).

## Available evidence and missing trigger

The report says an `Insert` reached `GetFreeIndexPage` with
`freeIndexPageList` pointing to an index page whose persisted `PageListSlot` was
1. It contains no LiteDB version, connection string, schema or index
declarations, record values, operation history, threading/process model,
standalone program, data file, WAL, or attachment. The only issue comment asks
for those details and reports earlier unsuccessful churn attempts. A `gh` search
for the exact diagnostic found no second issue or public reproduction.

The issue was filed on 2022-06-01, after 5.0.11 and before 5.0.12, so 5.0.11 is
plausible but not confirmed. This matters to the claimed Debug/Release
difference. In tag `v5.0.11`, `ENSURE` calls `Debug.Fail` and does not then throw
when a debugger is attached. PR #2094 changed it to throw after notifying the
debugger, but that change was first released in 5.0.12. Current dev calls
`Debugger.Break()` and then always throws `LiteException.InvalidDatafileState`.
Thus “works in Debug” may only mean that the old guard was swallowed; it is not
evidence that the data structure was healthy.

## Contract checked

Slot 1 is a valid state for an index page, but it means that the page has less
than `MAX_INDEX_LENGTH` (currently 1,400 bytes) free and is **not** on an index
free list. Slot 0 means reusable and linked. `AddOrRemoveFreeIndexList` removes a
page when it transitions from slot 0 to slot 1 and adds it on the inverse
transition; `GetFreeIndexPage` dereferences the list head and correctly requires
slot 0. Allowing slot 1 in that guard would hide a disagreement between the
collection page and index page and could pass an undersized page to
`InsertIndexNode`.

The bounded probe therefore used a two-sided oracle after every mutation phase:

- Follow every collection index's `FreeIndexPageList`, rejecting missing pages,
  cycles, cross-collection links, duplicate membership, non-index pages,
  `PageListSlot != 0`, fewer than 1,400 free bytes, and inconsistent backward
  links.
- Enumerate every index page independently and require the inverse: a page is in
  exactly one free-list chain if and only if its slot is 0; every slot-1 page has
  both links cleared.
- Compare all stored documents with an external ID/version ledger and resolve
  every expected row independently through each of two unique secondary
  indexes. This detects fixes that merely remove the `ENSURE`, unlink or drop
  records, skip index maintenance, or make scans look healthy while lookups are
  wrong.

## Natural reproduction attempts

The temporary xUnit probe (not retained as a regression test because it did not
reproduce the bug) exercised:

1. 180 rows and two unique secondary indexes whose keys alternate between
   roughly 30 and 900 characters. Across 24 rounds it updated most rows,
   deleted/reinserted the rest, committed 16 rounds, rolled back 8 rounds, and
   forced 6 duplicate-key failures. It checkpointed and reopened four times.
2. Four concurrent writers owning 48 IDs each, in both same-collection and
   separate-collection variants. Each variant ran 96 explicit transactions
   across 24 synchronized rounds (72 commits and 24 rollbacks), with a
   checkpoint/reopen after each group of six rounds.
3. A 300-row commit/update/rollback/update/commit sequence with
   `TransactionPageLimit = 8`. Before each transaction ended, `$transactions`
   had to report the eight-page limit and a nonzero `pagesInLogFile`, proving
   that the workload actually crossed safepoints. State and free lists were
   checked again after checkpoint and reopen.

The structural inverse check ran after every round as well as after checkpoint
and reopen. None of these natural operations left a slot-1 page reachable from
an index free-list head, and no insert raised the reported diagnostic.

As a sensitivity control only, the probe checkpointed a healthy file, changed
byte 13 (`PageListSlot`) of a referenced free index page from 0 to 1, and changed
nothing else. The independent structural check rejected the forged state, and
the next indexed insert threw `this page should be in slot #0`. This proves both
that the oracle detects the exact state and that the state explains the symptom;
it does **not** reproduce the operation that originally created the state.

The natural sequential and same-/separate-collection writer cases were also run
against the 5.0.11 NuGet package. The legacy checker combined `$page_list`,
`$dump(pageID)`, raw header byte 13, and forward/backward pointers to enforce the
same inverse-membership rule. All three cases passed there too.

## Results on dev

The relevant production blobs in base dev
`094f2b8564d65ae37951e4d15104c624c53dafdd`, Release-run worktree
`4e83efeb89e8309784f5cf79cf5291502c002ec6`, and Debug-run worktree
`a6ef654ac8917036b63c5c0ab473acc6a44192bf` are identical. Environment: Linux,
.NET SDK/runtime 8.0.30.

The isolated project referenced the current `LiteDB.csproj` with
`TestingEnabled=true`; isolation avoided unrelated, concurrently drafted issue
tests included by the main test project's glob.

```sh
dotnet test /tmp/issue2195-tests/Issue2195.Tests.csproj -c Release \
  --no-build --no-restore --settings "$PWD/tests.runsettings" \
  --filter FullyQualifiedName~Issue2195_Probe \
  --logger 'console;verbosity=normal'
```

Result: `Passed: 5, Failed: 0, Skipped: 0` in 13.4572 seconds. Four are
controls/probes of healthy behavior; the artificial-corruption case is only a
sensitivity control, not a natural repro.

```sh
dotnet test /tmp/issue2195-tests/Issue2195.Tests.csproj -c Debug \
  --no-restore --settings "$PWD/tests.runsettings" \
  --filter FullyQualifiedName~Issue2195_Probe \
  --logger 'console;verbosity=normal'
```

Result: `Passed: 5, Failed: 0, Skipped: 0` in 16.5600 seconds. The same natural
operations remained healthy in Debug; the forged control still raised the exact
guard.

Historical-package checks used `LiteDB` 5.0.11 from NuGet in a separate net8.0
test project. Sequential churn passed in 4.8542 seconds, same-collection writers
passed in 5.0663 seconds, and separate-collection writers passed in 4.7499
seconds. Those results show only that these bounded workloads are healthy; they
do not prove that every historical workload was safe.

## Status and next evidence needed

No executable natural reproduction can be derived from the report, so adding a
green test would mislabel an invariant canary as a regression for #2195. The
issue remains unconfirmed on dev.

The highest-value next artifact is a copy of the failing `.db` together with its
matching `-log.db`, captured before rebuild or another write. At minimum, a new
report needs the exact LiteDB assembly version, complete connection string,
index declarations and representative record, the last successful and first
failing operation sequence, whether multiple threads or processes write, and
whether the process can be terminated during a write. With a failing file, the
free-list head, page header, WAL generation, and neighboring links can be
preserved as a fixture while a separate operation-level repro searches for the
corruption source.
