# Issue 1467: reported row overwrite after physical power loss

Source: https://github.com/litedb-org/LiteDB/issues/1467 (open on
2026-09-14; labelled `question` and `needs more information`).

## Status

**No faithful regression is retained.** The report describes an indirect
Entity Framework duplicate-key error after repeatedly cutting power to a
device. The reporter later inferred that fields from one LiteDB row had
overwritten another row, and mentioned a separate historical
`EmptyPage`-to-`CollectionPage` cast. No LiteDB version, connection mode,
storage medium, update program, damaged database, or matching WAL survives.
Those observations are not enough to reconstruct which write was acknowledged
or which bytes changed.

The issue's own bounded current-`dev` investigation repeatedly killed a child
which rewrote 60 self-identifying rows, then tried truncated and torn WAL
tails. Every ordinary kill/reopen ledger remained intact; deliberately damaged
WALs produced other errors, never the reported cross-row overwrite.

During this sweep a stricter candidate ReproRunner was also tried. It put the
key in independent numeric/text fields, used a unique secondary index and a
payload checksum, and gated mid-transaction, immediately-before-commit,
immediately-after-commit, and selected internal WAL writes. The Direct-mode
boundaries preserved the exact all-old or all-new 60-row ledger. The broader
candidate was discarded: its internal write hook does not exist in the NuGet
assembly, and its Shared healthy control itself timed out, so retaining it
would confuse a harness/Shared-lifecycle failure with #1467's alleged row
overwrite.

A process kill is also not a substitute for physical power removal: it leaves
the kernel, filesystem, controller, and device caches alive. A permanently
green SIGKILL test could therefore make this issue appear fixed without testing
the reported failure boundary.

## Required evidence and future oracle

The highest-value artifact is the `.db` and matching `-log.db` copied after the
first failed boot and before LiteDB, an explorer, rebuild, or cleanup opens
either file. It should be accompanied by the exact LiteDB assembly/version,
connection string, filesystem and storage hardware, and the smallest update
loop that was running at power loss.

A future hardware or power-cut harness must keep an external, fsynced receipt
for every acknowledged generation and encode each row's identity at least four
independent ways: `_id`, a unique export ID, a textual identity, and a checksum
over the ID/generation/payload. After every cut it must verify:

- exact row cardinality and primary-key set;
- every full field and checksum through raw enumeration and `FindById`;
- the unique secondary index maps each export ID to exactly one matching row;
- transaction-wide generation atomicity, allowing only the complete previous
  or complete acknowledged generation; and
- the same ledger after checkpoint and a second reopen.

The negative control must intentionally corrupt/cross-wire two rows and prove
the oracle detects it. Lost acknowledged commits (#2818), foreign-WAL replay
(#2785), concurrent free-list corruption (#2825), and a generic failed-open
exception are related but must not be relabelled as this specific cross-row
overwrite without matching evidence.
