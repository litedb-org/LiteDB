# Issue #2795: offset pagination loads every skipped document

## Reported boundary

`Query().Skip(n).Limit(k)` becomes slower as `n` grows because `QueryPipe`
currently calls `LoadDocument(nodes)` before applying `Skip`. The same work is
done for `OrderBy(indexedField)` because the optimizer consumes that ordering
and leaves the pipe with an already ordered index-node stream. The desirable
bounded improvement is not constant-time B-tree access: traversing `n` index
nodes is expected, but deserializing the `n` skipped documents is not.

The issue consolidates the UI-pagination report in #1861 and the repeated chunk
scan in #2092. The latter turns linear work per page into quadratic work over a
complete collection scan.

## Regression oracle

`LiteDB.Tests/Issues/Issue2795_Tests.cs` uses the actual storage engine,
optimizer, selected index, index runner, `DatafileLookup`, and query pipe. A
counting decorator around the real lookup records every document
deserialization. No stopwatch threshold or cache behavior is involved.
This is deliberately an internal `QueryPipe` contract because the public reader
does not expose its lookup; the companion guard test exercises the public API.
The pipe receives a real in-memory `SortDisk`, not a null test substitute.

Four ledgers are checked independently:

1. Full returned documents are compared with page signatures calculated from
   the fixture formula, including `_id`, reverse sort key, proof integer, and an
   independent FNV hash of every character in a nonuniform 4 KiB payload.
2. The index-node ledger may visit between `limit` and `offset + limit` entries,
   allowing either a future direct seek or today's linear B-tree traversal, but
   it must end on the exact requested page and must not eagerly drain the index.
3. The loader ledger must contain exactly the `limit` document ids returned to
   the caller, regardless of which `IDocumentLookup` overload a future pipeline
   uses.
4. The deserialized payload-character total must be `limit * 4096`, independent
   of the offset.

`Issue2795_PipelineGuards_Tests` closes the tempting false fix from the other
side. Through the public fluent API, it proves that `Skip` remains after a
document predicate and `Offset` remains after a non-indexed sort. It also checks
that those execution plans really retain their filter and document sort. Moving
offset ahead of every load would make the performance test green but these
semantic guards red.

The public API also checks both `Skip` and `Offset` after a file close/reopen,
in ascending and descending indexed order. Its independent CLR ledger covers
the first page, a middle page, a partial last page, the exact end, and an offset
beyond the collection. Every stored row is checked after pagination. A separate
DbRef case requires `IncludeBefore` and a residual filter, verifies the referenced
payloads, and inspects the raw reference to prove those fields were not stored
inline. This catches moving offset ahead of reference expansion/filtering.

The test runs the default `_id` scan, an explicit ascending order backed by the
`$.sequence` index, and a descending `$.sequence` range whose predicate is fully
consumed by that index. Offset zero is a control for the first two routes;
offset 2,000 is the regression case. It also proves that the optimizer consumed
the indexed ordering and did not switch to the index-key-only loader.

A superficial change to the result order, execution-plan text, timing, cache,
or returned projection cannot satisfy the exact lookup ledger. Conversely, a
change that merely stops loading skipped rows but returns the wrong page fails
the independent semantic signatures.

## Expected result on current dev

Run:

```text
dotnet test LiteDB.Tests/LiteDB.Tests.csproj -c Release -f net8.0 \
  -p:TestingEnabled=true --filter FullyQualifiedName~Issue2795
```

The current implementation returns the correct pages but the test is red: the
late page invokes the document loader 2,007 times instead of seven. The intended
fix applies offset to the safe, already ordered index-node stream before
`LoadDocument`; document-level filters, includes, and unresolved sorts must keep
their existing ordering because those operations genuinely require documents.

Rechecked on 2026-09-14 after merging `dev` at
`a50661a9d1a25b5713586d0096c6325d76bf5dfe`: the original loader ledger still
fails for precisely the three late-page cases (2,007 loads instead of seven).
The public API guard cases pass. No production fix is included.

Sensitivity checks were run with temporary, uncommitted pipeline changes:

- Moving offset ahead of *every* document load: the loader ledger passes, but
  both the document-filter/sort guard and the DbRef-filter guard fail
  (11 pass, 2 fail).
- Moving it only when there are no residual filters, `IncludeBefore`, or
  unresolved ordering: all 13 cases pass.
- Restoring the original production source: the loader ledger fails again and
  all 12 semantic guards pass.

These checks demonstrate both rejection of the tempting shortcut and that a
correct improvement can satisfy the tests. The production file was restored
byte-for-byte after the experiments.

## Manual correction (2026-09-17)

Plans with no residual document filters, pre-filter includes or remaining sort
apply offset/limit to index nodes before loading payloads. Skipped nodes still
run transaction safepoints. Offset remains linear in index entries; use keyset
pagination for large repeated scans. Other plans keep document-level pagination.
