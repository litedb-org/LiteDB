# Issue 2765: [BUG] Opening an encrypted database without a password returns generic ErrorCode 0

Source: https://github.com/litedb-org/LiteDB/issues/2765 (open on 2026-09-12).

## Observed on dev

Base: `90788bace880f477c9fb52ff7c0da98c9700bdfe`; Release, .NET 8, Linux.
{'Failed': 1, 'Passed': 1}. Assertions describe correct behavior; failures are not skipped or inverted.

## Executed cases

- Passed: `Issue2765_Tests.Missing_and_wrong_passwords_report_structured_errors_without_altering_data(password: "incorrect")`
- Failed: `Issue2765_Tests.Missing_and_wrong_passwords_report_structured_errors_without_altering_data(password: null)`
  - The missing-password error uses generic code 0. The assertion accepts the
    existing `INVALID_PASSWORD` code or a future public password/encryption-
    specific code, while the wrong-password control remains exactly 217.

Run: `dotnet test LiteDB.Tests -c Release -f net8.0 -p:TestingEnabled=true --settings tests.runsettings --filter FullyQualifiedName~Issue2765_`.

## Manual correction

Both encrypted-header rejection paths now use the public INVALID_PASSWORD error
code while preserving the existing message that a password is required. Wrong
passwords keep their existing classification. Validation also covers missing
passwords on caller-owned streams, including ciphertext and stream ownership.
