# Issue 1513: periodic reads eventually time out entering transaction mode

Source: https://github.com/litedb-org/LiteDB/issues/1513 (open on
2026-09-13).

## Reproduction status

**The originating failure was not reproduced. No executable regression is
retained.** The complete issue, comments, and timeline were read with `gh`. The
report says only that an application upgraded from v4 to v5, read data about
once per minute, eventually threw

```text
LiteDB.LiteException: Database lock timeout when entering in transaction mode after 00:01:00
```

and worked again after its `-log.db` file was deleted. It supplies no code,
complete stack trace, exact LiteDB version, connection string, target runtime,
database/WAL pair, or description of how the process was stopped and restarted
around deletion. There is also no answer to the maintainer's questions about
`Checkpoint()`, `Rebuild()`, or an enumeration left open.

v5.0.3 was the latest tag when the issue was filed on 2020-02-26, but the report
does not say that this was the installed version. The transaction rewrite was
merged as `335035f1a6a0650030d1c6dbfa77215d99374d7c` on 2020-03-12 and shipped in
v5.0.4 that day. The only contemporary maintainer response asked the reporter
to retry that rewritten `master`; no result followed.

Deleting a WAL is not yet evidence that WAL contents caused the lock. In
particular, deleting an open `-log.db` on the reporter's likely Windows host
would ordinarily require closing the database or process first. That restart
would also discard every in-memory lock. The exact stop/delete/reopen sequence
is therefore essential.

## What the current lock path establishes

On current dev, the quoted `transaction mode` message has one direct source:
`LockService.EnterTransaction()` times out acquiring the read side of its
`ReaderWriterLockSlim`. Ordinary reads share that side and do not block one
another.

An explicit checkpoint takes the write side through
`WalIndexService.Checkpoint()` and `LockService.EnterExclusive()`. By contrast,
the size-triggered automatic checkpoint and normal close use `TryCheckpoint()`;
if a reader is active they return without queuing for the lock. Thus the mere
presence or age of a WAL cannot make new reads time out on this path.

A slow or abandoned query enumeration plus a concurrently queued explicit
checkpoint is one plausible way to manufacture the exact exception: the old
reader retains the shared lock, and the waiting writer prevents later readers
from entering. Neither half of that trigger appears in #1513. Adding both to a
test would demonstrate `ReaderWriterLockSlim` contention, not reproduce the
reported application. Related cursor-release cases already have focused tests;
duplicating one under this issue number would overstate the evidence.

## Bounded candidate probe

A temporary ReproRunner candidate exercised the strongest scenario actually
supported by the report and was removed after it stayed healthy. Its process
timeout was 90 seconds. For both Direct and Shared connection modes it:

1. persisted 97 deterministic documents and checkpointed setup;
2. reopened the database and made one header-only commit, leaving a confirmed
   8,192-byte WAL open in Direct mode (Shared mode's per-operation lifecycle
   checkpointed it to zero bytes, which the probe reported rather than hiding);
3. ran 512 sequential polling cycles per mode, with short bounded idle gaps;
4. on every cycle compared a full scan's exact IDs and checksum against an
   independent in-memory ledger, compared a bucket predicate's exact ID set,
   and checked a separately selected `FindById` value;
5. required the Direct WAL to remain live throughout polling, then required an
   explicit checkpoint to finish and truncate it; and
6. closed and reopened each database and rechecked exact row count and checksum.

The candidate returned `0` only for `LiteException.LOCK_TIMEOUT`, `10` only
after all progress/WAL/integrity/reopen checks passed, and `20` for any unrelated
failure. Its manifest required both exit code `10` and the final
`VERIFIED_1513` sentinel, so swallowing an exception, returning no rows, losing
data, or simply deleting the WAL could not produce a green run.

The final comparison command was:

```text
dotnet run --project LiteDB.ReproRunner/LiteDB.ReproRunner.Cli/LiteDB.ReproRunner.Cli.csproj --configuration Release -- run Issue_1513_PeriodicReadsProbe --report /tmp/issue-1513-report-v504.json --report-format json
```

Results on Linux / .NET 8:

- LiteDB 5.0.4 package: exit `10`, 1,024 cycles and all independent checks
  passed in 2.818 seconds.
- PR #2877 worktree source at
  `7b425e07c6e88307b2c110ffc60dbbd69111146a`: exit `10`, the same checks
  passed in 1.590 seconds. The PR's `dev` base was
  `094f2b8564d65ae37951e4d15104c624c53dafdd`; no production `LiteDB/` source
  differed between that base and the tested parent.
- A separate reporter-era 5.0.3 attempt did not reach the lock question: after
  `InsertBulk` reported 97 writes and setup was explicitly checkpointed, its
  first Direct scan returned zero rows and the strict harness exited `20` in
  0.229 seconds. That different early-version wrong-result behavior is not
  relabelled as #1513.

This is a bounded lifecycle check, not a simulation of an unknown multi-hour
timing condition. It shows that fully consumed periodic reads, including reads
while a real WAL remains present, do not reproduce #1513 on dev. It cannot show
that the original bug is fixed because the operation which queued or retained
the conflicting lock remains unknown.

## Evidence needed for an honest regression

A faithful ReproRunner should be added only after obtaining at least:

- the exact LiteDB package version, OS/runtime, and full connection string,
  especially Direct versus Shared;
- the query and SQL-upload loop, including where every `IEnumerable` or reader
  is materialized/disposed and whether it crosses an `await`, timer callback, or
  thread;
- whether any thread or process calls `Checkpoint()`, `Rebuild()`, or disposes
  the database while polling, and whether Studio or another process opens the
  same file;
- the complete exception stack plus all-thread stacks or a dump during the
  60-second wait;
- the last good `.db` and matching `-log.db` pair, their sizes, and whether the
  process was restarted before and after the log was deleted; and
- poll duration, overlap/reentrancy, time to first failure, and whether a single
  long-lived `LiteDatabase` or a new instance is used for each poll.

With those inputs, the regression should isolate each process, use barriers
rather than sleeps for the reported overlap, and independently assert forward
progress, exact data identity/checksums, WAL preservation and checkpoint
behavior, and successful close/reopen. Merely asserting that one query no longer
throws would be insufficient.
