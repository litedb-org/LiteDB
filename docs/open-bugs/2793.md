# Issue 2793: cross-account shared mutex and AppContainer admission

The Windows cross-account case is now **historically reproduced**. In
[CI run 34921553080](https://github.com/litedb-org/LiteDB/actions/runs/34921553080),
LiteDB **5.0.19 failed in 3/3 attempts** with `UnauthorizedAccessException`
naming the `Global\<hash>.Mutex` from the `SharedEngine` constructor.
**Dev `a50661a9` passed all 3 attempts.** The test source was
`aee3548876b5d47aa4e31ca9c861e23b98ed7082`; its production tree and C# probe match
this PR. The retained PowerShell driver additionally enforces these observed
package/source outcomes and rejects unknown results or non-mutex denials.

The owner runs as real LocalSystem (`S-1-5-18`), and the peer as a distinct local
account. The peer first opens the exact database in Direct mode and verifies
its payload, excluding data-file ACL failures. The owner then holds the actual
shared mutex. A successful peer must wait for release, write its row, and leave
both exact payloads readable by an independent reopened database. The package
failure must leave the owner's row intact. Earlier CI setup failures are not
counted as bug evidence.

The separate **UWP/AppContainer case remains unverified**: a LocalSystem/user
comparison does not exercise an AppContainer token. The existing Direct-mode
control and explicitly skipped platform case remain honest about this boundary.

## Regression contract

`Issue2793_Tests` deliberately does not fake AppContainer status. It queries the
Windows access token's `TokenIsAppContainer` field and skips the regression
unless the test host really has an AppContainer token. In that environment it:

1. creates and independently reopens the database in Direct mode, proving that
   the AppContainer can write the selected path;
2. opens the same database in Shared mode and independently opens the expected
   `Local\\<name>.Mutex`, deriving the documented default name separately from
   LiteDB's mutex-name factory;
3. holds that Local mutex while a different thread starts a LiteDB write, and
   requires the write to stay blocked until the independent handle releases it;
4. closes Shared mode, reopens through a new Direct connection, and requires the
   exact control and shared payloads.

Those checks prevent making the test green by swallowing the constructor error,
silently using Direct mode, creating an unused Local mutex, or acknowledging a
write that never becomes durable. The separate Direct-mode fact is a portable
healthy control for the same write/reopen oracle.

There is no injectable OS-call seam in `SharedMutexFactory`: it statically calls
a private P/Invoke implementation. Treating every synthetic
`ERROR_ACCESS_DENIED` in an ordinary desktop process as permission to switch to
a Local mutex would be an unsafe test contract, because it can split cooperating
processes into different lock domains. This regression therefore uses the real
platform boundary rather than source-text assertions or a misleading denial
simulation.
