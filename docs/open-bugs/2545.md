# Issue 2545: `DropCollection` fails after a stale WAL is replayed

Source: https://github.com/litedb-org/LiteDB/issues/2545 (open on 2026-09-13).

The issue's deterministic reproduction restores an older copy of a data file
beside a WAL captured from a later generation of that same database. On dev,
LiteDB replays the incompatible WAL, one `DropCollection` fails with `Page type
must be data page: {0}`, and later drops report that the thread already has an
open transaction.

`Issue2545_Tests` exercises both sides of the contract. The healthy control
provides the matching data-file generation with the exact same WAL and requires
all twelve collections to replay, drop, and stay dropped after reopening. The
regression case provides the old generation and accepts either safe rejection
at open or safe isolation of the stale WAL. If open succeeds, the four backup
collections and their external payload ledger must remain exact, every drop
must succeed, and a replacement generation must persist across reopen. This
prevents a fix that simply ignores all WAL files, suppresses drop errors, or
leaves acknowledged writes only in memory.

A separate test deliberately continues through the issue's `DropCollection`
loop. Every catalogued collection must either drop successfully or retain a
clear `LiteException`; neither that loop nor a follow-up insert may expose an
unexpanded `{0}` placeholder or the unrelated “already contains an open
transaction” error. This isolates #2545's transaction-cleanup symptom even
though the incompatible-WAL cause is also tracked by #2785.

The fixture uses `MemoryStream` pairs to avoid platform timing and filesystem
cache effects while exercising the same engine WAL recovery path. It does not
claim to identify how the reporter's original Xamarin/MAUI files became
mismatched.

Dev context: `89820a3b0a8575e6d126d0b7ff6a9b920dc2078b`, rebased PR #2877 worktree,
Linux / .NET 8. The matching-WAL control passed. The restored-generation test
failed because opening exposed all four `mid*` and all four `late*` collections
in addition to the four `base*` collections. That proves dev replayed the later
WAL instead of rejecting or isolating it; the assertion stops before relying on
the secondary symptoms. The continued drop-loop test independently failed when
a later drop reported `The current thread already contains an open transaction`
after the first failed automatic transaction. Total: one passed, two failed in
one second.
