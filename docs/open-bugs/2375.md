# Issue 2375: Uno WebAssembly loses LiteDB updates across page close

Source: https://github.com/litedb-org/LiteDB/issues/2375 (open on
2026-09-14; labelled `question`, `needs more information`, and
`severity: critical`).

## Status

**No faithful executable regression is retained.** The report is credible at
the Uno/IDBFS persistence boundary, but it does not establish a defect that a
native LiteDB test can exercise. It supplies no project, LiteDB or Uno version,
connection string, storage path, database/log pair, browser, close/reload
script, or independently acknowledged write ledger. The reporter has not yet
answered the maintainer's 2026 request for those details.

Current `dev` passes the existing native external-stream checkpoint and reopen
suite. Uno's own WebAssembly implementation, however, still separates
synchronous `System.IO` writes from asynchronous IndexedDB persistence. A
LiteDB `Checkpoint()`, `Dispose()`, or `FileStream.Flush()` can complete after
updating Emscripten's in-memory filesystem without proving that Uno's later
`FS.syncfs` callback committed those bytes to IndexedDB.

A native green test would therefore let this issue appear fixed while never
crossing the reported durability boundary. A mock async stream would have the
opposite problem: it would reproduce data loss by construction without showing
that the reporter's Uno/browser combination behaves that way.

## The platform boundary exists in both relevant Uno generations

Uno 4.10.13 resolves to
`aa0c4019cf2b6d2388e9df5af261be7ff154a853`. Its
[`StorageFolder.ts`](https://github.com/unoplatform/uno/blob/4.10.13/src/Uno.UI/ts/Windows/Storage/StorageFolder.ts#L23-L105)
has these durability properties:

1. It mounts `IDBFS` with empty options, not `autoPersist: true`.
2. Initial restore calls `FS.syncfs(true, callback)` asynchronously.
3. Save-to-IndexedDB is requested every 10 seconds and by a `beforeunload`
   listener which invokes `synchronizeFileSystem(false)` without awaiting a
   completion value.
4. `_isSynchronizing` admits only one operation. If a save is requested while
   another sync is in flight, the method simply returns; it does not queue the
   newer generation.

Those exact timer, unload-listener, mount, callback, and single-operation-gate
semantics remain in current Uno `master`; the current TypeScript blob inspected
on 2026-09-14 was
`bff035fe665d7755edbb06c25ef723b0185dcd0e`. Uno PR
[#7876](https://github.com/unoplatform/uno/pull/7876) intentionally introduced
the gate in 2022 to eliminate concurrent `FS.syncfs` warnings, not to provide a
queued persistence barrier.

The matching historical
[`file-management.md`](https://github.com/unoplatform/uno/blob/4.10.13/doc/articles/features/file-management.md#L32-L53)
states that WebAssembly storage uses Emscripten IDBFS, only designated
application-data folders persist across refreshes, initialization is
asynchronous, and an awaited `StorageFolder` operation is required before using
`System.IO` so the previous IndexedDB contents have first been loaded. The same
warning remains in current Uno documentation.

Emscripten's
[`Filesystem-API.rst`](https://github.com/emscripten-core/emscripten/blob/main/site/source/docs/api_reference/Filesystem-API.rst#L168-L186)
documents the other half of the contract: ordinary writes are temporary and
in-memory by default, while `FS.syncfs` performs persistence. Its
[`syncfs` reference](https://github.com/emscripten-core/emscripten/blob/main/site/source/docs/api_reference/Filesystem-API.rst#L349-L379)
explicitly describes synchronization as asynchronous.

This yields two distinct candidate failure windows, neither yet tied to the
reporter's code:

- opening LiteDB through `System.IO` before Uno finishes its initial
  `syncfs(true)` can observe an empty/stale virtual filesystem; and
- closing/reloading after LiteDB flushes MEMFS but before a completed
  `syncfs(false)` can restore the prior IndexedDB generation. The final request
  can also be skipped if Uno's gate is already occupied.

The LiteDB 5.0.17 and current `EngineSettings.DataStream` documentation also
says not to use a `FileStream` as a custom stream and to use `Filename` for a
physical file. The reporter's manual-stream experiment is therefore useful
diagnostic context, not a documented durability remedy.

## Bounded current-dev probes

The exact tested LiteDB source was `origin/dev`
`a50661a9d1a25b5713586d0096c6325d76bf5dfe`. At probe time the checked-out
production tree matched that revision; the issue-test branch had no local
production diff under `LiteDB/`. On Ubuntu 24.04 / Linux x64, .NET 8.0.30, this
command passed all three tests:

```text
dotnet test LiteDB.Tests/LiteDB.Tests.csproj -c Release -f net8.0 \
  -p:TestingEnabled=true --no-restore \
  --filter FullyQualifiedName~IssueCheckpointFlush_Tests

Passed! - Failed: 0, Passed: 3, Skipped: 0, Total: 3
```

The suite verifies that a caller-owned native `FileStream` retains an updated
document after commit, durable stream flush, stream disposal, garbage
collection of the undisposed database wrapper, and independent reopen; that
the stream constructor's forced checkpoint setting is restored; and that a
checkpointed file reopens through a read-only stream. These are valuable
negative controls, but Linux `FileStream` has no asynchronous
IDBFS-to-IndexedDB layer.

A second bounded schedule check copied the 4.10.13/current synchronization
gate exactly and supplied a controlled asynchronous `FS.syncfs`. Generation 1
was captured by a periodic sync, LiteDB-equivalent synchronous writes advanced
MEMFS to generation 2, and `beforeunload` requested another save before the
first callback. The observed states were:

```json
{"phase":"beforeunload-return","memoryGeneration":2,"indexedDbGeneration":0,"syncCalls":1,"synchronizing":true}
{"phase":"first-sync-complete","memoryGeneration":2,"indexedDbGeneration":1,"syncCalls":1,"synchronizing":false}
```

Thus the gate did not enqueue generation 2. This proves the source-level
schedule, not that a real browser selected it during #2375. The model was not
retained as a ReproRunner because an implementation copied from Uno will stay
red even if LiteDB, Uno, or browser lifecycle behavior changes independently.

This host has no Uno template/workload and no Chromium/Firefox executable. The
installed .NET templates include Blazor WebAssembly only. Adding a current Uno
sample would still not reconstruct the omitted 2023 package versions,
application startup path, file location, or reload timing.

## Required browser regression and double-entry oracle

A faithful repro needs the reporter's minimal project or a new Uno WebAssembly
app which deliberately specifies every missing variable. It must run in an
actual browser and use separate page instances so a reopen really repopulates
MEMFS from IndexedDB. At minimum the harness must:

1. Pin the LiteDB assembly, Uno packages/bootstrapper, target framework,
   browser build, IDBFS configuration, connection string, and exact path under
   `ApplicationData.Current.LocalFolder`.
2. Await `LocalFolder.CreateFolderAsync` before any `System.IO` access. Also run
   a deliberately unawaited startup as a sensitivity control, but never accept
   that race as the primary repro.
3. Create a durable baseline generation, close the first page only after a
   completed IndexedDB sync, reopen, and prove every baseline row is present.
4. For each later generation, store `_id`, generation, unique token, payload,
   and a checksum of all fields. Keep the expected ledger in the Playwright
   host (outside IDBFS) before closing the page.
5. Exercise both the supported filename path and the reporter's separate
   caller-owned data/log streams. Record exact data/log lengths and SHA-256
   hashes in MEMFS and, independently, the corresponding IndexedDB records.
6. After each acknowledged insert/update/delete batch, call `Checkpoint()` and
   `Dispose()`, then close or reload immediately. Repeat with a delay longer
   than the 10-second timer and with an explicitly awaited `FS.syncfs(false)`
   callback as controls.
7. On a fresh page, await initial population and compare the database against
   the host ledger by full scan, `FindById`, and a unique-token index. Require
   exact count, key set, generation, payload, and checksum, then checkpoint and
   verify the same ledger after a second reopen.
8. Test close while an earlier sync is deliberately held in flight. Observe
   whether the final request is dropped and which exact IndexedDB generation is
   restored.
9. Make the oracle prove itself: replace only the data record, only the log
   record, and both records with the prior generation in separate negative
   controls. Each must report the precise lost/stale rows instead of merely
   accepting any open failure.

Run that matrix against LiteDB 5.0.17 plus the reporter's actual package if
different, and against a clean current-`dev` consumer; likewise test the
historical Uno package graph and current Uno. A valid fix must either provide
and use an awaited persistence barrier before acknowledging safe close, retain
all acknowledged generations across immediate reopen, or explicitly reject an
unsupported browser persistence configuration before writes are accepted.
Waiting for the timer, swallowing open errors, recreating an empty database, or
making only the native control green does not resolve the reported data loss.
