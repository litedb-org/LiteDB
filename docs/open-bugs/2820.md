# Issue 2820: Opening a file that is not a v5 LiteDB database modifies it: files under 8 KB are overwritten with an empty database, larger ones are truncated

Source: https://github.com/litedb-org/LiteDB/issues/2820 (open on 2026-09-12).

## Observed on dev

Base: `9fe924c8b134550da4801be382d9062bd5da901e`; Release, .NET 8, Linux.
`9 failed, 2 passed, 11 total`. Assertions describe correct behavior; failures are not skipped or inverted.

## Executed cases

- Passed: an empty file remains a usable new database.
- Passed: a 229,376-byte genuine v5 database with a 5,003-byte torn tail is trimmed back to its exact checkpoint image in writable mode; all 96 patterned rows and the indexed lookup survive, and a post-recovery sentinel persists across checkpoint and read-only reopen.
- Failed (six theory rows): patterned foreign files of 16, 8,192, and 20,009 bytes are not safely rejected in either writable or read-only mode.
  - The 16-byte writable case is silently replaced by an 8,192-byte database; the read-only case is truncated to zero.
  - The 20,009-byte cases are truncated to 16,384 bytes.
  - The 8,192-byte cases stay byte-identical but throw `ArgumentOutOfRangeException`, not `LiteException.INVALID_DATABASE`.
  - Every row independently checks rejection type, exact length, SHA-256, full byte sequence, and released file handle.
- Failed (two theory rows): opening the repository's real encrypted v4.1 fixture without `Upgrade=true` truncates it from 20,480 to 16,384 bytes in both writable and read-only modes. The fixed path must preserve the fixture's known SHA-256, then explicitly upgrade it, verify both exact source documents, write a sentinel, checkpoint, and reopen it.
- Failed: read-only recovery can query the complete 96-row ledger in a torn v5 file, but destructively trims its 5,003-byte tail. The expected contract keeps the full 234,379-byte image and its SHA-256 unchanged.

Run: `dotnet test LiteDB.Tests/LiteDB.Tests.csproj -c Release -f net8.0 -p:TestingEnabled=true --no-restore --filter FullyQualifiedName~Issue2820_`.

## Current-source platform difference (2026-09-15)

On current `dev` source `a50661a9`, the read-only torn-tail preservation case
passes all nine Linux/macOS CI jobs but fails all twelve Windows x64/x86 jobs
across .NET 8, 9, and 10. Windows still trims the expected 234,379-byte image
to 229,376 bytes. This accounts for one additional issue-test failure on Windows;
the foreign-file and encrypted-v4 rejection regressions remain red everywhere.
