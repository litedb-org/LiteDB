## Historical dispose-failure reproduction (2026-09-15)

A one-time log metadata I/O failure during disposal leaves a real data-file handle
locked on **5.0.20 in 3/3 attempts**. The test holds the database object alive and
tries an exclusive OS file open before any GC, finalization, or disposal retry.
On **dev `a50661a9`, all 3 attempts pass**, including exclusive file admission,
reopen with the original committed payload, a new write, and a second reopen.
These initial observations were on Linux; the Windows follow-up below now
exercises the same lifecycle test on an actual Windows runner.

## Windows cleanup and CI follow-up (2026-09-15)

Windows temporary-file deletion previously replaced the leaked-handle assertion
with a cleanup exception. The test now captures the exclusive-open failure while
the database is alive, finalizes the historical leak only after that observation,
and rethrows the original assertion before temporary-file cleanup. Dev must still
release the handle without GC or a disposal retry and pass both reopen ledgers.

Windows Server 2022, Ubuntu 22.04, and Ubuntu 24.04 now each reproduce the historical
leak **3/3** and pass dev **3/3**. The runner accepts only the ownership assertion;
an unrelated cleanup exception cannot count as proof.
