# Issue 2867: inherited `<MappedTypeName>Id` is not recognized as the id

Source: https://github.com/litedb-org/LiteDB/issues/2867 (open on 2026-09-13).

## Contract and independent checks

When `InheritedInvoice` inherits an `InheritedInvoiceId` property from a base class, that property must map to `_id`. The fixture verifies that reflection really reports the base as `DeclaringType` and the mapped derived class as `ReflectedType`, so it exercises the reported distinction rather than an ordinary declared-property convention.

The checks cover both sides of the mapping and the storage boundary:

- Mapper-authored BSON must contain the supplied integer as `_id`, must not retain a second `InheritedInvoiceId` field, and an independently authored `{ _id, Payload }` document must hydrate the inherited property.
- Two typed inserts are closed and reopened with a fresh mapper. Untyped `FindById` and `Query.EQ("_id", ...)` inspect the durable raw documents, while typed `FindById` and the inherited-member predicate check the public query path.
- Inserting the same inherited id twice must hit the primary-key unique index and leave one document. Generated `ObjectId` values therefore cannot make the regression green.
- Healthy controls retain the already-supported directly declared `<TypeName>Id` convention and `Id` precedence. An unrelated inherited `SomeoneElsesId` remains a normal field, preventing a blanket inherited-`*Id` rule.

The case is small and deterministic, so the unit-test harness provides tighter mapper, persistence, and query oracles than a separate ReproRunner process.

## Observed on dev

Tested base: `3156633cfa0cfd2fd48d55abcb02bd092c287edb`; Release, Linux.

Run:

`dotnet test LiteDB.Tests/LiteDB.Tests.csproj -c Release -f net8.0 -p:TestingEnabled=true --settings tests.runsettings --filter FullyQualifiedName~Issue2867_ --no-restore`

Result: 4 total, 1 passed, 3 failed, 0 skipped. The mapper emits `Payload`/`InheritedInvoiceId` instead of `_id`; typed insertion consequently returns an auto-generated non-`Int32` id; and a duplicate `InheritedInvoiceId` is accepted instead of raising `INDEX_DUPLICATE_KEY`. The direct-convention, `Id`-precedence, and unrelated-suffix controls pass. Assertions state the corrected behavior and are neither skipped nor inverted.
