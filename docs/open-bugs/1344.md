# Issue 1344: overlapping FileStorage uploads to one id throw a duplicate chunk key and lose the replacement

Source: https://github.com/litedb-org/LiteDB/issues/1344 (open on 2026-09-13).

The report has no comments or attached database/project. It was filed against
4.1.4 on Xamarin UWP and Android. The reporter says the work should be
single-threaded, so concurrency is **not** a directly reported precondition.
It is inferred from the supplied log: the same `EGyVJ_MU4AEM1k-.jpg` id enters
the stream-save path twice before either invocation finishes, output for other
tweet ids is interleaved, and the eventual duplicate chunk belongs to that
repeated id.

The regression therefore isolates that inferred race on one `LiteDatabase`
instance, whose supported surface is advertised as thread-safe. It does not
copy the report's simultaneous short-lived Direct connections, network access,
or platform-specific Xamarin code, any of which would confound the FileStorage
race.

## Deterministic schedule and anti-shortcut ledger

Both tasks call the public `Upload` API for `$/tweet/image.jpg`. The first
source pauses on its first read, which is after `OpenWrite`; the replacement
then reaches the same point. The replacement supplies no bytes until the first
upload has returned, so a correct implementation has an unambiguous final
value: the complete replacement. The first wait has a two-second escape hatch
and the whole test has a 30-second limit, allowing a fix which serializes
same-id uploads to complete instead of deadlocking in the test gate.

The deterministic byte patterns deliberately span several chunks:

- unrelated sentinel: 261,157 bytes;
- first target generation: 522,353 bytes;
- replacement target generation: 783,617 bytes.

Chunk boundaries depend on the source read/flush pattern. Partial intermediate
chunks are valid; the test requires nonempty bounded chunks and checks metadata
counts against the actual contiguous stored sequence.

Before close and again through a fresh database instance, the test checks the
exact file-id set, filenames, lengths and chunk counts. It independently reads
the raw `_chunks` collection, requires every chunk to have a live owner and a
contiguous zero-based number, concatenates raw chunk bytes, and compares them
with the generated ledger. Public `Download` bytes and `FindById().Length` must
agree. The sentinel closes off a "repair" which clears unrelated storage; the
raw and reopened checks close off merely swallowing the exception or changing
metadata.

## Historic NullReferenceException distinction

Version 4.1.4's `LiteFileStream` finalizer called `Dispose(false)`, and that
path called `Flush` even after an earlier dispose-time chunk insertion failed.
Because `_disposed` was assigned only after `Flush`, a later finalizer-thread
retry could escape the caller's `try/catch`. Commit
`9511ebe8d905f123cb1dd4ff4285459100a2f8a6` removed the finalizer four days
after this report. Dev no longer reproduces that uncatchable
`NullReferenceException`; it still reproduces the duplicate-key failure and
lost replacement proven above.


## Concurrent deletion and metadata follow-up

The manual review reproduces a delete/upload race: deletion can commit removal of
the old file record, wait for an upload, then remove that upload's chunks after
it recreated its file record. Delete now checks for an existing record, then
runs both removals inside an empty file-update batch. The engine acquires the
file write lock and transaction before enumerating that batch; nested file and
chunk removals join the same transaction. No document is yielded or updated; a concurrently dropped collection is not recreated.
OpenWrite acquires the same file lock before reading metadata or touching chunks,
so both Upload and caller-owned transactions use that order. The lock-only update
does not create missing collections.
An absent record leaves incremental OpenWrite chunks untouched. Standalone
OpenWrite keeps its established incremental behavior. Arbitrary caller collection
writes retain the engine's normal lock-timeout behavior if they acquired
collections in a conflicting order.

SetMetadata supplies a lazy update, so it reads the current file only after
acquiring the file write lock and maps it with the existing serializer hooks.
This prevents a stale metadata update from replacing upload length/chunk/filename
fields while preserving custom serializers and arbitrary mapped field names.
It does not touch the chunk collection or invalidate an active chunk cursor.
Empty file operations do not create a chunk collection.

Issue1344Delete/Composition/Metadata/SharedReader/Decorator/StorageCompatibility
tests cover paused uploads, atomic deletion, caller rollback, open unrelated
cursors, incremental writers, direct/shared mode, metadata races, serializer
mappings, and forwarding engines. Engine decorators must preserve the existing
single-pass streaming enumeration contract: buffering input already breaks typed
Insert's generated-ID handoff at baseline. Fresh concurrent uploads are covered.
The corrected original fixture still fails the original baseline with duplicate
keys and wrong payloads; it passes with the earlier #2806 upload transaction fix
plus this follow-up.

Read-to-write snapshot upgrades retain the original snapshot for active cursors,
including its original WAL view across safepoints. Retention is conservative
while any cursor is active because Include pipelines cache secondary snapshots. Transaction commit, rollback,
and error cleanup release those retained leases. Missing-collection snapshot
replacement acquires the new lock before releasing the old one, preventing a
first-creation race. Transactional incremental writers, active file cursors,
post-precheck collection drops, and read-view preservation after write/safepoint
are covered explicitly.

Retaining a pipeline's existing snapshot does not establish whole-query snapshot
isolation across writes. If Include switches reference collections and later
reacquires one, it sees the transaction's current snapshot, preserving baseline
read-your-writes behavior. The cycling-reference regression passes against both
67b214cc and this correction.
