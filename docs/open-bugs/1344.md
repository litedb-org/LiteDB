# Issue 1344: overlapping FileStorage uploads to one id throw a duplicate chunk key and lose the replacement

Source: https://github.com/litedb-org/LiteDB/issues/1344 (open on 2026-09-13).

The report has no comments or attached database/project. It was filed against
4.1.4 on Xamarin UWP and Android. The reporter says the work should be
single-threaded, so concurrency is **not** a directly reported precondition.
It is inferred from the supplied log: the same `EGyVJ_MU4AEM1k-.jpg` id enters
the stream-save path twice before either invocation finishes, output for other
tweet ids is interleaved, and the eventual duplicate chunk belongs to that
repeated id.

The regression therefore isolates that inferred race on one `LiteDatabase`
instance, whose supported surface is advertised as thread-safe. It does not
copy the report's simultaneous short-lived Direct connections, network access,
or platform-specific Xamarin code, any of which would confound the FileStorage
race.

## Deterministic schedule and anti-shortcut ledger

Both tasks call the public `Upload` API for `$/tweet/image.jpg`. The first
source pauses on its first read, which is after `OpenWrite`; the replacement
then reaches the same point. The replacement supplies no bytes until the first
upload has returned, so a correct implementation has an unambiguous final
value: the complete replacement. The first wait has a two-second escape hatch
and the whole test has a 30-second limit, allowing a fix which serializes
same-id uploads to complete instead of deadlocking in the test gate.

The deterministic byte patterns deliberately span several chunks:

- unrelated sentinel: 261,157 bytes / 2 chunks;
- first target generation: 522,353 bytes / 3 chunks;
- replacement target generation: 783,617 bytes / 4 chunks.

Before close and again through a fresh database instance, the test checks the
exact file-id set, filenames, lengths and chunk counts. It independently reads
the raw `_chunks` collection, requires every chunk to have a live owner and a
contiguous zero-based number, concatenates raw chunk bytes, and compares them
with the generated ledger. Public `Download` bytes and `FindById().Length` must
agree. The sentinel closes off a "repair" which clears unrelated storage; the
raw and reopened checks close off merely swallowing the exception or changing
metadata.

## Historic NullReferenceException distinction

Version 4.1.4's `LiteFileStream` finalizer called `Dispose(false)`, and that
path called `Flush` even after an earlier dispose-time chunk insertion failed.
Because `_disposed` was assigned only after `Flush`, a later finalizer-thread
retry could escape the caller's `try/catch`. Commit
`9511ebe8d905f123cb1dd4ff4285459100a2f8a6` removed the finalizer four days
after this report. Dev no longer reproduces that uncatchable
`NullReferenceException`; it still reproduces the duplicate-key failure and
lost replacement proven above.
