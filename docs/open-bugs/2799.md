# Issue 2799: network-backed storage rejects `FileStream.Flush(true)` during checkpoint/close

Source: https://github.com/litedb-org/LiteDB/issues/2799 (open on 2026-09-13).

## Existing fixture assumptions and independent checks

The regression replaces the data-file pool with an `IStreamFactory` that returns a
real `FileStream` subclass. Its `Flush(true)` override records the call and throws
`UnauthorizedAccessException`, while `Flush()` and `Flush(false)` remain healthy and
are counted as fallbacks. A generic custom `Stream` would be a false control:
`StreamExtensions.FlushToDisk` only selects the Boolean overload for `FileStream`,
and the public stream constructor wraps its stream in `ConcurrentStream`.

The rejecting case requires two acknowledged inserts, a successful explicit
checkpoint, and a successful close. It also requires one plain fallback for the
explicit failure, a second fallback/checkpoint during close, and an empty WAL.
After close it copies **only** the data file to a different path and reopens that
copy, where both IDs and payloads must match exactly. This prevents WAL recovery
or exception swallowing from hiding a data-file readability failure. It proves
ordinary reopen behavior, not power-loss durability: the OS or remote server may
still hold unflushed data in volatile caches. An otherwise identical healthy factory proves the fixture really
reaches `FileStream.Flush(true)` and that normal forced-flush persistence works.

## Observed on dev

Base: `89820a3b0a8575e6d126d0b7ff6a9b920dc2078b`; Release, .NET 8, Linux.

```sh

  -p:TestingEnabled=true --no-restore --settings tests.runsettings \
  --filter FullyQualifiedName~Issue2799_
```

Result: **1 failed, 1 passed**. The healthy control passed. The rejecting case
reached `Flush(true)` twice and failed because explicit `Checkpoint()` propagated
the synthetic `UnauthorizedAccessException`, no plain fallback occurred after

The acknowledged inserts, in-session read, data-only reopen, and exact two-row
payload check did not fail.

## Real-share limitation

This is a deterministic simulation of the exact reported .NET failure boundary;
it is not an SMB, CIFS, NFS, or Azure filesystem emulator. It cannot validate
redirector-specific locking/oplocks, SMB dialects, intermittent failures, or the
exception mapping on a particular server. A final fix still needs a Windows retest
on an affected UNC share and Azure App Service `D:\home`. Shared mode across
multiple machines remains unsupported independently of this flush regression.

## Deferred from the manual sweep (2026-09-17)

The user requested skipping this report in the sweep and retaining it for later
planning, potentially with an explicit setting through which an application
chooses storage compatibility versus durability. No fallback or storage-policy
change is made by this deferral. The retained tests remain executable evidence;
their expectation of automatic fallback is not an approved durability contract.

Considerations for that design:

- Keep durable flushing required by default. An ordinary `Flush()` cannot replace
  the guarantee requested by `Flush(true)` when the storage backend rejects it.
- Consider an explicit opt-in option with a clearly defined scope: commits,
  checkpoints, WAL identity/generation metadata, truncation, encryption wrappers
  and caller-owned streams must agree on the selected policy.
- A failed forced flush can also indicate a real permission or I/O fault. Do not
  silently treat every failure as an unsupported network-storage capability.
- Checkpoint cannot establish that the data is crash-safe merely because ordinary
  flush or reopen succeeds. Truncating the WAL before data is durable can lose
  acknowledged writes or leave inconsistent database state after a crash.
  The option's documented guarantees must account for recovery ordering too.
- Surface relevant errors and the selected policy so applications can make an
  informed choice. Preserve resource cleanup independently of durability policy.
- Validate failure handling and recovery ordering with fault-injection tests,
  then test actual affected Windows UNC/SMB and Azure storage. Ordinary reopen
  checks alone do not establish power-loss safety.

This is a design agenda, not a chosen API or a promise that relaxed flushing is
safe for every filesystem. See also [WAL recovery identity](../wal-recovery-identity.md).
