# Issue 2839: LongCount(Query) counts through the int Count() path, so it can't exceed int.MaxValue

Source: https://github.com/litedb-org/LiteDB/issues/2839 (open on 2026-09-12).

## Observed on dev

Base: `de578c6eff264a688662a5dfa800009c25533a4b`; Release, .NET 8, Linux.
`2 passed, 1 failed`. Assertions describe correct behavior; the failure is not
skipped or inverted.

## Executed cases

- Passed: `Issue2839_Tests.Count_Query_routes_the_exact_query_and_reads_an_Int32_result`
  - The `Query` route returns the distinct, Int32-safe value 1,234,567,890.
- Passed: `Issue2839_Tests.LongCount_without_Query_preserves_an_engine_result_above_Int32`
  - The sibling overload returns 2,147,483,748, proving the fake and normal
    `LongCount()` path preserve Int64 values.
- Failed: `Issue2839_Tests.LongCount_Query_routes_the_exact_query_and_preserves_Int64_width`
  - The exact query route returns 4,294,967,303.
  - System.OverflowException : Value was either too large or too small for an Int32.

## Independent oracle

The engine double validates the aggregate projection, collection, parameterized
route predicate, descending order, offset, and limit. It derives a different
result from each validated route instead of returning a configurable constant.
Consequently, changing `LongCount(Query)` to use a working no-argument overload
while discarding the caller's query cannot make the target test pass. Separate
tests pin the Int32 `Count(Query)` path and the full-width no-argument
`LongCount()` control. Routed queries must also retain their options and restore
their original projection after execution.

Run: `dotnet test LiteDB.Tests -c Release -f net8.0 -p:TestingEnabled=true --settings tests.runsettings --filter FullyQualifiedName~Issue2839_`.
