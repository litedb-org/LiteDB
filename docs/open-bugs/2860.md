# Issue 2860: relative `Uri` values cannot be read back

Source: https://github.com/litedb-org/LiteDB/issues/2860 (open on 2026-09-13).

## Contract and independent checks

A `System.Uri` property must survive mapping and persistence with both its text and
its absolute/relative kind intact. The regression suite keeps two independent
ledgers:

- independently authored BSON strings are mapped to CLR objects, so the read-side
  assertion does not trust LiteDB's serializer to create its own fixture;
- typed values are inserted into an in-memory database, the raw BSON string is
  checked against `System.Uri.ToString()`, and the typed value is then read back.

The matrix contains ordinary and parent-relative paths, the Unix-sensitive `/a/b`
case, and absolute HTTP, URN, and `file:` controls. The absolute controls prevent a
fix that simply constructs every value as relative; pairing `/a/b` with
`file:///a/b` prevents a blanket leading-slash or file-path workaround.

The issue also carries the source fork's max-depth diagnostic change. Two nested
CLR types deliberately have the same simple name (`Node`) but different full
names. Each assertion checks error code 201 and the complete, exact message. A
change that continues to print only `Type.Name` therefore cannot satisfy the
test.

All cases are bounded, use only an in-memory database, have no skips or inverted
assertions, and are compiled into every `LiteDB.Tests` target framework.

## Expected correct result

All 14 cases pass. Relative URI strings deserialize without `UriFormatException`,
`/a/b` remains relative on every platform, absolute values remain absolute, raw
BSON contains the URI's textual value, and max-depth errors identify the exact CLR
type with `Type.FullName`.

## Observed on dev

Dev baseline tested: `89820a3b0a8575e6d126d0b7ff6a9b920dc2078b`,
with `Issue2860_Tests.cs` added and no production changes; Release, Linux.

Commands run for each test target:

```bash
dotnet test LiteDB.Tests/LiteDB.Tests.csproj -c Release -f net8.0 -p:TestingEnabled=true --settings tests.runsettings --filter 'FullyQualifiedName~Issue2860_'
dotnet test LiteDB.Tests/LiteDB.Tests.csproj -c Release -f net461 -p:TestingEnabled=true --settings tests.runsettings --filter 'FullyQualifiedName~Issue2860_'
dotnet test LiteDB.Tests/LiteDB.Tests.csproj -c Release -f net481 -p:TestingEnabled=true --settings tests.runsettings --filter 'FullyQualifiedName~Issue2860_'
```

The `net8.0` run discovered 14 cases: 6 absolute-URI controls passed and 8 cases
failed. Both ordinary relative strings throw `UriFormatException` in each of the
independently-authored and database paths; `/a/b` is incorrectly returned as an
absolute URI in both paths; and both diagnostic cases print only `Node` rather
than either full CLR name. This independently confirms both defects are still
present.

The stock `net461` and `net481` commands stop before test discovery on an existing
`Issue1162_Tests.cs` dynamic-binder compilation error
(`Microsoft.CSharp.RuntimeBinder.CSharpArgumentInfo.Create`). In a disposable
verification worktree, supplying that pre-existing missing framework reference
allowed this test file to compile into both target assemblies; execution then
aborted because this Linux host has no Mono runtime. No framework-specific guard
or exclusion was added to the regression.

As a satisfiability check, a disposable copy using relative-or-absolute URI
deserialization (with `/a/b` explicitly retained as relative) and `Type.FullName`
for the diagnostic passed all 14 `net8.0` cases. Those production edits are not
part of this regression-test change. Current status: **reproduced**.
