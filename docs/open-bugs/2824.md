# Issue 2824: Rebuild() on an encrypted database: parameterless call leaves a plaintext file ("File is not encrypted"), password change throws "Invalid password"

Source: https://github.com/litedb-org/LiteDB/issues/2824 (open on 2026-09-14).

## Observed on dev

Base: `4eca573513de1e7e95fa72b74a954fb179eb728f`; Release, .NET 8, Linux.
`10/10` cases failed. Assertions describe correct behavior; failures are not
skipped or inverted.

## Executed cases

- Failed in Direct and Shared modes:
  `Parameterless_rebuild_retains_encryption_and_the_current_password`.
  Both calls replaced the active encrypted file with plaintext and then threw
  `LiteException` 216 (`File is not encrypted`).
- Failed in Direct and Shared modes:
  `Rebuild_with_a_new_password_propagates_it_to_the_active_engine`.
  Both calls created the new-password file but reopened it using the old
  password and threw `LiteException` 217 (`Invalid password`).
- Failed in Direct and Shared modes:
  `Explicit_null_password_removes_encryption_without_disposing_the_active_engine`.
  Both calls created the requested plaintext file but left the active engine
  configured with the old password, then threw `LiteException` 216.
- Failed for encrypted and plaintext databases in both Direct and Shared modes:
  `Bare_sql_rebuild_is_parameterless_and_never_dereferences_null`.
  All four cases threw `NullReferenceException` because the SQL parser passes
  null to the rebuild engine.

## Independent oracles

The tests distinguish a missing options object from an explicitly supplied
`RebuildOptions` whose password is null. Parameterless API and bare SQL rebuilds
must preserve the current password, while the explicit null must remove
encryption. Each contract runs through Direct and Shared engines; the next
operation on the same Shared `LiteDatabase` therefore detects a stale password
in `SharedEngine` rather than accepting a fix limited to the temporary engine.

Every successful rebuild must preserve two non-contiguous pre-rebuild receipt
rows, accept and checkpoint a third row through the same instance, and reproduce
the exact ordered ledger after a fresh reopen. The durable header marker must be
exactly `1` for encrypted output and `0` for plaintext output. Fresh opens then
prove the precise accepted password and the established rejection codes for old
or wrong passwords. A missing password must still be rejected, but its error
code belongs to #2765 and is deliberately not duplicated here. The test
snapshots the complete database bytes around rejected opens to prevent a
write/delete or repair-on-failure implementation from satisfying only the
visible password checks.
