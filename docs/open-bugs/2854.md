# Issue 2854: circular Snapshot page-list walks are unbounded

Source: https://github.com/litedb-org/LiteDB/issues/2854 (open on
2026-09-14).

## Observed on dev

The `Issue_2854_CircularPageList` ReproRunner case reproduces on package
5.0.21 and current `dev`; both variants exit `0` with
`BUG_2854_CONFIRMED`.

An independent raw-page parser proves a healthy collection owns 32 data pages
and that all 32 occur exactly once in its free-list chain. The fixture changes
only the four-byte tail-next and head-previous fields, making that reachable
chain circular, then verifies every edge and collection/slot/page identity.

On current `dev`, `DropCollection` silently completes instead of rejecting the
corrupt list. A separate read-only `SELECT $ FROM $page_list` process remains
in the walk until the harness kills its process tree after the exact five-second
deadline.

## Double-entry checks

- Separate child processes run healthy drop and `$page_list` controls first;
  the drop persists and the system query yields every independently identified
  page exactly once without changing the file.
- Corrupt drop and system-query probes use separate byte-identical copies, so
  one operation cannot repair or poison the other's evidence.
- Every dangerous operation is bounded by a parent-side deadline, process-tree
  termination, and bounded output draining; the regression suite itself cannot
  hang.
- A fixed result must be `LiteException.INVALID_DATAFILE_STATE` (999), with the
  exact cycle intact and only LiteDB's one-byte recovery marker changed.
- Silent completion, the known unsafe cast, or a verified timeout reproduces
  the issue. An unrelated exception, crash, malformed fixture, missing marker,
  or incomplete child output is a harness failure rather than a false fix.

```sh
dotnet run --project LiteDB.ReproRunner/LiteDB.ReproRunner.Cli -- \
  run Issue_2854_CircularPageList
```
