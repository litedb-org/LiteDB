# Issue 2818: Committed transactions are lost on power loss or OS crash: commits never fsync the log file, and encrypted databases never fsync at all

Source: https://github.com/litedb-org/LiteDB/issues/2818 (open on 2026-09-14).

## Observed on dev

Base: `789d57d814a463396305657db0742cb86350429a`; Release, .NET 8, Linux.
`1 passed, 2 failed`. Assertions describe correct behavior; failures are not skipped or inverted.

The regression stream now stops inside `FileStream.Flush(true)`. The test races that
explicit entry signal against `Commit()` itself: a correct commit must reach the gate
first and remain incomplete until the gate is released. The ten-second waits are only
deadlock guards; the durability assertion is based on signal ordering and commit state
while the flush is deterministically held. A separate passing control proves the gate
does not publish bytes until the forced flush is released.

After release, recovery uses only snapshots taken after `Flush(true)`, copied into
independent streams before disposal can rescue them. The ledger begins with two
checkpointed rows, then updates one, inserts a multi-page value, and deletes the other.
Exact raw IDs and payloads are checked after recovery for both plain and encrypted
streams, so calling fsync before the WAL write cannot make the test green.
