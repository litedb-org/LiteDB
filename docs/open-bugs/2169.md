## Historical and current checkpoint-error reproduction (2026-09-15)

The new public-Insert scenario reproduces the disposed-transaction rollback error
on **5.0.11 and dev `a50661a9`, 3/3 attempts each**. Eight workers first insert
800 rows. A one-time access-denied error during a subsequent automatic checkpoint
is replaced by `transaction must be active to rollback`. All 808 committed IDs
and independently computed worker/payload fields survive checkpoint and reopen;
a further write succeeds before the exception-identity assertion fails.
This proves a concrete cause of the reported symptom, without claiming that the
reporter's machine had the same storage fault.

## Recovery-stream correction (2026-09-15)

Full CI at `3c061833` exposed an unrelated test-fixture failure on Ubuntu 24.04:
the 5.0.11 recovery checkpoint sometimes needed more pages than the fixed-capacity
byte-array MemoryStream could hold. The runner correctly rejected the resulting
`NotSupportedException: Memory stream is not expandable` as unrelated evidence.

Recovery now uses an expandable stream. All 808 committed rows, computed worker
and payload values, and the worker index are verified; a recovery insert and
checkpoint are followed by a second read-only reopen checking all 809 rows. Only
then is the original checkpoint exception identity asserted. The runner's exact
failure classification is unchanged. **25/25 attempts on 5.0.11 and 25/25 on dev**
reach the intended disposed-rollback assertion after these controls pass.
