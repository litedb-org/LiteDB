# Issue 2849: safepoint write cost

Source: https://github.com/litedb-org/LiteDB/issues/2849

The ReproRunner fixture did **not** reproduce a twofold slowdown at its default
100,000-row scale on dev `90788bace880f477c9fb52ff7c0da98c9700bdfe`
(.NET 8, Linux). This is an honest no-repro result, not evidence that the larger
workload in the issue is fixed.

The fixture compares three alternating samples using the default transaction
page limit and a 100,000-page control. It times one transaction inserting 2 KB
payloads and a subsequent half-dataset delete. Outside the timed regions it
checks counts, then reopens each database and verifies every surviving ID and
payload. A shortcut that omits work therefore fails the persistence ledger.

Observed median ratios, default divided by the large-budget control:

- NuGet 5.0.21: insert 0.984, delete 1.039. The page-limit setting is absent in
  that release, so both profiles are equivalent controls.
- Dev: insert 0.980, delete 0.993.

The manifest deliberately expects dev to reproduce the report, so the runner
reports an unmet expectation while retaining all measurements. Use
`LITEDB_REPRO_ROWS=1000000` during the post-PR investigation to approach the
reported workload; the three-sample comparison can then take several minutes.

```sh
dotnet run --project LiteDB.ReproRunner/LiteDB.ReproRunner.Cli -c Release -- run Issue_2849_SafepointCost
```
