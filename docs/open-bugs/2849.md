# Issue 2849: random-key transaction page-budget cost

The original sequential insertion/full-scan deletion workload did not reproduce
this defect, even at one million rows. Restoring shuffled IDs and shuffled `IN`
deletions makes pages be revisited beyond the default transaction page budget.
The earlier literal-IN workload reproduces on both the reported commit and current dev:

| Production source | Insert median ratio | Delete median ratio | Persistence checks |
| --- | ---: | ---: | --- |
| `90788bace880f477c9fb52ff7c0da98c9700bdfe` | 2.942 | 2.352 | Passed |
| `a50661a9d1a25b5713586d0096c6325d76bf5dfe` | 2.962 | 2.384 | Passed |

Each ratio compares the default budget with 100,000 pages across three alternating
sample pairs. The threshold remains 2x. Every surviving ID and its independently
computed payload must persist after reopen before measurements can count.
The strengthened driver also checks the complete inserted dataset before deletion
and refuses a source build missing the configurable page-budget control.
LiteDB 5.0.21 has no such setting; it is a workload/data control only.

[Runner, environment, and command](../../LiteDB.ReproRunner/Repros/Issue_2849_SafepointCost/README.md).
[Historical/current raw sample timings](evidence/2849-20260915.json).
Performance runs must be isolated from other benchmarks; a smaller passing run
or a successful runner process alone is not a fix verdict.

## Windows expression-literal failure (2026-09-15)

The original million-row fixture terminates with a stack overflow during the
compiled IN-list evaluation on Windows, on both 5.0.21 and dev. That process
failure is unrelated to the page-budget ratio and is not performance evidence.
The driver now passes the same shuffled IDs as a `BsonArray` query parameter,
preserving the single deletion transaction and all data/reopen controls. A
1000-row control passes both variants; it is not a million-row performance result.

The completed parameterized fixture on Linux x64/net8.0, production dev `a50661a9`,
measures **2.911x inserts and 2.495x deletes** (three alternating pairs). All six
complete inserted-row and reopened-survivor ledgers pass before these ratios count.

[Original Windows failure](evidence/2849-windows-literal-20260915.json),
[parameterized local samples](evidence/2849-parameterized-local-20260915.json).

The exact reported source `90788bac` also reproduces with the same parameterized
fixture: **2.924x inserts and 2.455x deletes**, with all six complete data ledgers
passing. Both local comparisons use net8.0 Release production builds and the same
fixture source blob. [Historical parameterized samples](evidence/2849-parameterized-historical-20260915.json)
also retain the build project used to link the retained driver to that source.
