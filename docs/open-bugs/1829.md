# Issue 1829: predicate composition changes `Count()` by operand order

Source: https://github.com/litedb-org/LiteDB/issues/1829 (open on 2026-09-13).

The complete issue body and all six comments were reviewed with `gh`. The report
uses the same four products reproduced below and the invocation-based
`PredicateBuilder` already present in the test suite. There are no uploaded
assets or linked standalone repro projects.

## Contract and independent checks

`Issue1829_Tests` preserves the reported `false OR Name.Contains("a")` query in
both operand orders. It also composes two predicates that contribute disjoint
matches, so an implementation that silently ignores either operand cannot pass.
Each case first checks a hard-coded in-memory truth table, then checks a direct
LINQ expression against LiteDB, the exact sorted result IDs, query enumeration
cardinality, server-side `Count()`, and the untouched four-row collection.

The expected issue-data matches are IDs 4 and 7. The stronger two-live-predicate
case expects IDs 4, 5, and 7. `AssertQuery` evaluates enumeration and `Count()`
before opening one assertion scope; therefore a false aggregate cannot hide a
wrong row set, and a coincidentally correct aggregate cannot hide wrong IDs.

The third pair is the compatibility guard described by the maintainer in the
issue. It manually creates distinct outer and inner `ParameterExpression`
instances with the same name and evaluates the semantics
`outer.Scores.Any(inner => inner > outer.Id)`, while both expression parameters
are named `p`. It then composes that predicate in both orders. This prevents
fixing #1829 by comparing parameter names and thus regressing nested `$` versus
`@` scope resolution.

## Observed on dev

Clean upstream `dev` checkout tested:
`56272498975c7fbdbf28ad2a63cac064b7ae8454`; Release, Linux. The issue test was
the only source injected into that detached checkout, through a temporary
`CustomAfterMicrosoftCommonTargets` file; no production source was changed.

The exact modern-target commands were:

```sh
dotnet test LiteDB.Tests/LiteDB.Tests.csproj -c Release -f net8.0 \
  -p:TestingEnabled=true \
  -p:CustomAfterMicrosoftCommonTargets=/tmp/litedb-issue1829-include.targets \
  --settings tests.runsettings \
  --filter FullyQualifiedName~Issue1829_ --logger "console;verbosity=detailed"

dotnet test LiteDB.Tests/LiteDB.Tests.csproj -c Release -f net10.0 \
  -p:TestingEnabled=true \
  -p:CustomAfterMicrosoftCommonTargets=/tmp/litedb-issue1829-include.targets \
  --settings tests.runsettings --filter FullyQualifiedName~Issue1829_ \
  --logger "console;verbosity=detailed"
```

Both .NET 8.0.30 and .NET 10.0.11 produced the same result: **3 passed, 3
failed**. The .NET Framework targets described below produced the identical
result. Assertions state correct behavior and are neither skipped nor inverted.

- Failed: reported case with `false` first. Enumeration returned exact IDs 4 and
  7, but `Count()` returned 0 instead of 2.
- Passed: the same reported case with `Contains` first; IDs 4 and 7 and count 2.
- Failed: two-live-predicate case with the ID predicate first. Enumeration
  returned exact IDs 4, 5, and 7, but `Count()` returned 1 instead of 3.
- Passed: the same two-live-predicate case with `Contains` first; IDs 4, 5, and
  7 and count 3.
- Failed: same-name nested predicate with `false` first. Enumeration returned
  exact IDs 4 and 7, but `Count()` returned 0 instead of 2.
- Passed: the same nested predicate first; IDs 4 and 7 and count 2.

This is a deterministic current-dev reproduction. A ReproRunner process fixture
would add no relevant environment boundary, so the regression stays in the unit
test project beside the existing predicate-builder and LINQ mapper coverage.
