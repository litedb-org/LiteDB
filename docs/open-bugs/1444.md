# Issue 1444: ObjectId timestamps wrap in 2038

Source: https://github.com/litedb-org/LiteDB/issues/1444 (open on 2026-09-13).

## Report and contract

The 2020 report asked why `NewObjectId` computes Unix seconds as `long` and
then narrows them to `int`. Its only maintainer reply called this a very old
implementation and promised a review; no fix or compatibility decision
followed. On 2026-09-13 the issue was reclassified from `suggestion` to `bug`
and renamed to describe the concrete consequence: the signed value wraps at
the 2038 boundary, reversing ordering and `CreationTime`.

The accepted BSON ObjectID specification defines the first four bytes as a
big-endian **unsigned** Unix-seconds value. Its test plan names these exact
oracles:

| Timestamp bytes | Unsigned seconds | UTC creation time |
| --- | ---: | --- |
| `00000000` | 0 | `1970-01-01T00:00:00Z` |
| `7fffffff` | 2,147,483,647 | `2038-01-19T03:14:07Z` |
| `80000000` | 2,147,483,648 | `2038-01-19T03:14:08Z` |
| `ffffffff` | 4,294,967,295 | `2106-02-07T06:28:15Z` |

The public `Timestamp` property may remain a signed `int` containing the same
32 bits for compatibility. The regression therefore independently
reinterprets that raw value as `uint` rather than requiring a breaking public
API change. Correct unsigned interpretation is required for creation time and
comparison.

Specification: https://github.com/mongodb/specifications/blob/master/source/bson-objectid/objectid.md

## Regression boundary and controls

`Issue1444_Tests` enters each timestamp twice: once through an explicit
12-byte array and once through an independently written 24-character hex
string. Both paths must preserve every byte through `ToByteArray`, `ToString`,
their inverse constructors, and Extended JSON. They must also expose the exact
unsigned timestamp bits and UTC creation time above. The epoch and last signed
second are healthy controls for the two post-2038 cases.

Adjacent-pair checks require `CompareTo`, all relational operators, and
`BsonValue.CompareTo` to agree across the full unsigned range. The fixture also
checks same-timestamp suffix ordering so a timestamp fix cannot ignore the
remaining eight bytes. Finally, four documents are inserted in reverse order;
`FindAll` must return their exact ObjectIds in unsigned primary-index order.
This is both a BSON persistence round trip and a user-visible index-order
oracle.

## Observed on dev

Latest fetched `origin/dev` was `a50661a9d1a25b5713586d0096c6325d76bf5dfe`.
The tested integration worktree's `LiteDB/Document/ObjectId.cs` was byte-for-byte
identical to that revision.

Release / .NET 8 command:

```sh
dotnet test LiteDB.Tests/LiteDB.Tests.csproj -c Release -f net8.0 \
  -p:TestingEnabled=true \
  -p:DefaultItemExcludesInProjectFolder='**/Issue2798_Tests.cs' \
  --no-restore --settings tests.runsettings \
  --filter FullyQualifiedName~Issue1444_Tests --verbosity minimal
```

Result: **9 total, 5 passed, 4 failed, 0 skipped**. The four failures are
independent manifestations of the same signed interpretation:

- `80000000` reports `1901-12-13T20:45:52Z`, not the next second in 2038;
- `ffffffff` reports `1969-12-31T23:59:59Z`, not the final second in 2106;
- `7fffffff...` compares greater than `80000000...`; and
- the primary index returns `80000000, ffffffff, 00000000, 7fffffff` instead
  of unsigned chronological order.

All raw byte, hex, constructor, JSON, signed-range ordering, post-boundary
ordering, suffix-ordering, and timestamp-bit controls pass. This proves the
wire representation is intact and isolates the defect to signed date and
comparison interpretation.

The test source compiled successfully in Release for `net461`, `net481`,
`net8.0`, and the opt-in `net10.0` target. During final verification the shared
integration worktree's unrelated `Issue2798_Tests.cs` did not compile, so the
commands excluded only that concurrently changed file. The complete remaining
project, including `Issue1444_Tests`, compiled for every target. An earlier
clean .NET 8 run before that unrelated change produced the same result, and
running the built `net10.0` fixture also produced the same **5 passed / 4
failed** split.
