# Issue 2891: Concurrent collection create/list races on HeaderPage._collections ("Collection was modified; enumeration operation may not execute")

Source: https://github.com/litedb-org/LiteDB/issues/2891 (opened on 2026-09-16, after the 2026-09-14 inventory snapshot).

## Observed on dev

Base: `a50661a9d1a25b5713586d0096c6325d76bf5dfe`; Release, `net8.0` test build run on the .NET 10 runtime (`DOTNET_ROLL_FORWARD=Major`), Windows x64.
{'Failed': 2} in 5 of 5 runs. Assertions describe correct behavior; failures are not skipped or inverted.
The same race also reproduces with a standalone program on the LiteDB 5.0.21 package and on dev `9b2f122f` (see the issue).

## Executed cases

- Failed: `Issue2891_Tests.Reading_cols_while_another_thread_creates_a_collection_does_not_throw`
  - Expected readFailure to be <null> because $cols must not enumerate the live header collection dictionary (#2891), but found System.InvalidOperationException: Collection was modified; enumeration operation may not execute.
  - Deterministic: the `$cols` reader holds `HeaderPage.GetCollections()` open while another thread commits a new collection.
  - Control: the writer's insert succeeds, and all four collections are listed afterwards.
- Failed: `Issue2891_Tests.Concurrent_first_inserts_into_new_collections_do_not_throw`
  - Expected failures to be empty because creating distinct collections concurrently must not race on HeaderPage._collections (#2891); first failure after 1 round(s): System.InvalidOperationException: Collection was modified; enumeration operation may not execute.
  - Stack: `BsonDocument.GetBytesCount` ← `HeaderPage.GetAvailableCollectionSpace` ← `CollectionService.CheckName` ← `CollectionService.Add`.
  - Timing dependent. Each fresh database is seeded with 300 collections in one transaction, which lengthens the unlocked header enumeration. Then 200 new collections get their first insert in parallel (at least 16 threads, or 4 × processor count). Rounds repeat until the first failure or a 12-second budget.
  - Locally it failed in the first round in 6 of 6 runs (about 0.3 s).
  - Control: every round that has no failure must list all 500 collections.

## CI evidence

- [Run 35107834796](https://github.com/litedb-org/LiteDB/actions/runs/35107834796) at `a1d93966`, before seeding existing collections: the `$cols` test failed in all 21 ordinary test jobs. The stress test failed in 18 of 21; the three `windows-2022 x64` jobs passed it within the 12-second budget. The seeded fixture above replaces that version.
