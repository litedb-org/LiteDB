# Issue 2320: signatures on the published package

The consumer artifact for exact dev commit
`a50661a9d1a25b5713586d0096c6325d76bf5dfe` is
`LiteDB.6.0.0-prerelease.181.nupkg`. On 2026-09-15, the retained script verified
its nuspec identity and source commit, then reproduced the defect:

- Package SHA-256: `b4bbb61cb5ada7b8aa8be517e8203fdc3574d0029543b3542741f88ef474c7a3`.
- NuGet verification accepts a NuGet.org Repository signature, but there is no
  SignPath Foundation Author signature.
- `lib/net10.0/LiteDB.dll`, `lib/net8.0/LiteDB.dll`, and
  `lib/netstandard2.0/LiteDB.dll` have no PE Authenticode certificate table.
- Exit 1, `BUG_2320_CONFIRMED`.

```sh
python3 scripts/regressions/issue_2320/verify_package_signing.py \
  --version 6.0.0-prerelease.181 \
  --expected-commit a50661a9d1a25b5713586d0096c6325d76bf5dfe
```

The same check previously reproduced missing signatures on published dev
`6.0.0-prerelease.114`, source `90788bace880f477c9fb52ff7c0da98c9700bdfe`.
The immutable 5.0.21 package is a positive control for the Author-signature
oracle. Its DLLs also lack Authenticode signatures: the DLL check proves an
unmet requested contract, not that DLL Authenticode once worked and regressed.

The test checks the artifact's version and source commit, cryptographically
verifies package signatures, and separately examines every embedded library's
PE certificate directory. Any certificate present must also pass a platform
Authenticode verifier. An unavailable verifier is a harness error, never a pass.
An old signed package, a Repository signature, strong-name signing, a dummy
certificate table, or signing configuration alone cannot satisfy these checks.

Local pack output precedes signing and has a distinct pre-sign-only outcome.
See [the script instructions](../../scripts/regressions/issue_2320/README.md).
