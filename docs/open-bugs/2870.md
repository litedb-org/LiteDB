# Issue 2870: query rethrows erase the original stack trace

Source: https://github.com/litedb-org/LiteDB/issues/2870 (open on 2026-09-13).

## Contract and independent checks

The regression registers an external system collection and reaches it only through
`LiteEngine.Query`. One source throws on its first `MoveNext`; the other returns a
verified document and throws on the next `IBsonDataReader.Read`. Together those
paths cross both `QueryExecutor` catch sites and the later-read catch in
`BsonDataReader`, so changing only one `throw ex;` cannot satisfy both tests.

Two more dynamic paths cover the other sites named by the issue. A previously
thrown, non-lock `IOException` is passed to `WaitIfLocked`; and a one-page stream
throws from `Read` while `FileReaderV8.Open` is loading its header. The latter is
captured by `ReadPage` and reaches the real `HandleError` rethrow. Each red
assertion requires the exact exception object, its distinct literal message, and
its no-inline origin frame. The query and file cases also verify exact read counts
and the file-reader error ledger.

Three controls close the opposite side: a healthy registered query source returns
all documents in order, a sharing-violation `IOException` returns normally from
`WaitIfLocked`, and `FileReaderV8` reopens a real checkpointed database and reads
back its exact ID and payload with an empty error ledger. Swallowing/wrapping
exceptions or disabling the underlying work therefore cannot make the suite
green.

## Observed on dev

Production base tested: `094f2b8564d65ae37951e4d15104c624c53dafdd`.
The relevant `QueryExecutor.cs`, `BsonDataReader.cs`, `FileReaderV8.cs`, and
`IOExceptionExtensions.cs` content was identical in the tested PR worktree.
Release, .NET 8, Linux:

```sh
dotnet test LiteDB.Tests/LiteDB.Tests.csproj -c Release -f net8.0 \
  -p:TestingEnabled=true --settings tests.runsettings \
  --filter FullyQualifiedName~Issue2870_Tests --no-restore
```

Result: 4 failed, 3 passed. The erased traces start at `QueryExecutor.cs:139`,
`BsonDataReader.cs:118`, `IOExceptionExtensions.cs:38`, and
`FileReaderV8.cs:576`; none retains its asserted origin frame. Exception identity,
literal messages, read counts, error-ledger checks, and all three healthy controls
pass before the frame assertions.

In a disposable validation copy, changing the two query rethrows and reader
rethrow to bare `throw;`, and the two parameter rethrows to
`ExceptionDispatchInfo.Capture(ex).Throw()`, made all seven tests pass (7 passed,
0 failed). No production fix is included in this regression commit.

The test source also compiled into `LiteDB.Tests.dll` for every declared test TFM.
The exact .NET Framework checks used an isolated copy and excluded the unrelated
PR test for #1162, which currently does not compile for `net461`:

```sh
DefaultItemExcludes='Issues/Issue1162_Tests.cs' dotnet test \
  LiteDB.Tests/LiteDB.Tests.csproj -c Release -f net461 \
  -p:TestingEnabled=true --settings tests.runsettings \
  --filter FullyQualifiedName~Issue2870_Tests --no-restore

DefaultItemExcludes='Issues/Issue1162_Tests.cs' dotnet test \
  LiteDB.Tests/LiteDB.Tests.csproj -c Release -f net481 \
  -p:TestingEnabled=true --settings tests.runsettings \
  --filter FullyQualifiedName~Issue2870_Tests --no-restore
```

Both produced their target DLL, then test execution aborted because this Linux
host has no Mono runtime. No .NET Framework execution result is claimed.
